## 一、存档格式（已实测确认）

```
{json0}${json1}$...${json13}
```

- **14 个独立 JSON 对象**，用 `$` 字符拼接
- 每段自带 `DateID` 字段标识段号（0~13）
- UTF-8、无 BOM、无加密、无压缩、无签名、无 CRC
- float 字段是"十进制舍入后写文本"格式（见 §五）

## 三、三项需求的实现点

### 需求 1：黄金树无限开通

**位置**：段 11

```json
{"DateID":11,"IsJiHuo":1,"IsHuangJin":1,"GuoQiTime":1594173000463,
 "JiHuoCiShu":2,"GuoShiIsLingQu":1,"GuoShiChongZhiTime":1592323200000}
```

| 字段 | 含义 | 改法 |
|---|---|---|
| `IsJiHuo` | 生命树激活标记 | 置 `1` |
| `IsHuangJin` | **黄金等级标记（独立字段）** | 置 `1` |
| `GuoQiTime` | 到期时间（Unix 毫秒，类型是 **ulong**） | 推到远期，如 `4102416000000` |
| `JiHuoCiShu` | 已激活次数 | 无需改动 |

**✅ 已解决（2026-10 实证）。** 早期"必须先确认续期公式"的怀疑被排除了：

决定性证据是三份官方存档的横向对比 —— `playerDate_01` / `02` 的 `GuoQiTime`
在 2020 年 7 月就已过期，但 `IsHuangJin` **仍然是 1**。
说明"黄金"是**独立保存的等级标志**，不是由到期时间推导出来的。

`dump.cs:263367` 的 `Date_ShengMingShu`（TypeDefIndex 3075）字段完整对应段 11：

```csharp
public uint  IsJiHuo;             // 0x14
public uint  IsHuangJin;          // 0x18  ← 黄金档，独立
public ulong GuoQiTime;           // 0x20  ← 到期时间（ulong）
public uint  JiHuoCiShu;          // 0x28
public uint  GuoShiIsLingQu;      // 0x2C
public ulong GuoShiChongZhiTime;  // 0x30
```

**一键修改**：

```bash
python savedit.py tree <存档> --out out.json
```

实测（playerDate_03，原 `IsJiHuo=0 IsHuangJin=0`）：
```
段11 后: IsJiHuo=1 IsHuangJin=1 GuoQiTime=4102416000000 (2099-12-31)
受影响段: [11]  字段: ['GuoQiTime', 'IsHuangJin', 'IsJiHuo']
```

还有 `get_GuoQiDay()`（`RVA 0x18A50FC`）会把到期时间折算成剩余天数给 UI 用，
所以改完之后界面显示的剩余天数会一起变成约 27000 天。

### 需求 2：宝石与宝石碎片 ✅ 最简单

**位置**：段 9

```json
{"DateID":9,"DangQianTiLi":40,"DangQianCengJi":3,"XianJiName":"",
 "ChongZhiTime":1592323200000,"BaoShiSuiPian":2655,
 "SuoYouBaoShiTongJi":{"baoShiZongShu":2282,"baoShiShu_Hong":680,...}}
```

**改 `BaoShiSuiPian` 一个整数即可。**

```
python savedit.py baoshi <存档> 999999
```

**⚠️ 不要动 `SuoYouBaoShiTongJi`。** 元数据有 `JiSuanTongJi`(计算统计)、`AddBaoShi`、`RemoveBaoShi`、`FenSuiBaoShi`，
这组数字是**行为累加出来的**，强改可能被重算或触发异常。只改消费入口最安全。

**真正的宝石实体**在段 1 的 `HerosDates[].HeroZhuangBeis[].XiangQianBaoShiID`，
示例 `[3106, 0, 0, 0, 0]`。宝石实例 ID 编码规则未知，**不建议手工构造**。

**相关属性（从元数据提取，用于 dump.cs 检索）**：

### 需求 3：宠物获取

**位置**：段 6

```json
{"DateID":6,
 "SuoYouChongWuDate":[{"ChongWuID":0,"ChongWuLevel":20,"ChongWuJinHua":1,
                       "ChongWuJinJie":10,"ChongWuYongJiu_HP":150,
                       "ChongWuYongJiu_Damage":100,"IsXieDai":0,"IsMaoXian":-1}, ... 共85个],
 "ChongWuSiLiao":315,
 "JinHuaShi_Feng":11,"JinHuaShi_Huo":8,"JinHuaShi_Shui":30,
 "JinHuaShi_Di":1,"JinHuaShi_Guang":26,"JinHuaShi_An":23}
```

**关键事实**：3 个官方演示档里 **85 个槽位全部有数据** —— 这是**固定 85 槽的图鉴**，不是背包。

**⚠️ 重要修正（2026-10 实证）**：`ChongWuDate`（`dump.cs:263195`）只有 8 个字段，
**没有任何"是否拥有 / 是否解锁"标志**。也就是说：

- **"获取宠物"这个需求在存档层不存在** —— 宠物本来就全在表里
- 能改的是**属性**：等级 / 进化 / 阶级 / 永久HP / 永久攻击
- 真正的"开放"是解锁宠物**玩法**，对应 `ChongWuPool.OpenAllChongWu()`（`dump.cs:256215`）

**属性强化（已实测）**：

```bash
python savedit.py pets <存档> --level 80 --jinhua 4 --jinjie 10 \
                             --hp 99999 --dmg 99999 --out out.json
```

实现用 `max(原值, 目标值)`，**只上调不下调**，不会把已培养的宠物改低。

**饲料/进化石路线（数值更小，更保守）**：
```
python savedit.py set <存档> 6.ChongWuSiLiao 9999
python savedit.py set <存档> 6.JinHuaShi_Feng 9999    # 风/火/水/地/光/暗 六种
```

**注意派生值**：`ChongWuYongJiu_HP` / `ChongWuYongJiu_Damage` 可能是按 `ChongWuLevel` + `ChongWuJinHua` 算出来的，
强改可能被重算覆盖。**优先改等级和进化石，让游戏自己算 HP。**

**抓宠机制（元数据发现）**：
- `ZhuaChongMiMa`（抓宠密码）+ `zhuaCiShu` / `zhuaCiShuMax`（抓宠次数）
- `KeZhuaChongWu`（可抓宠物池）、`YiZhuaChongWu`（已抓）、`ZhanDouChongWu`（战斗宠）
- `OpenAllChongWu` / `SaveAllChongWu` 方法存在 → **"全开"是游戏原生能力**

## 五、浮点格式（重要工程发现）

游戏对 double 的文本格式化**不是**标准的 shortest-round-trip，而是**十进制舍入后写文本**：

```
原文 1.5413264036178589  → double 精确等于 1.5413264036178589  (0 ulp)
原文 2.4295361042022707  → double = 2.4295361042022705         (+0.9 ulp)
原文 36.810935974121097  → double = 36.810935974121094         (+6.76 ulp)
```

**6 种格式化策略的复原率**（267 个独立值）：

| 策略 | 复原率 |
|---|---|
| Python `repr` (shortest) | 66.3% |
| ROUND_HALF_UP @17 有效位 | 66.3% |
| 精确值 ROUND_HALF_UP @17 | 19.1% |
| 二进制 ulp/2^24 对齐 | 5.2% |
| Java `Double.toString` | 66.3% |

**2026-10 补充实测**（用工具自身的 `roundtrip` 命令重新跑三份存档）：

| 存档 | 数字 token | **数值等价** | 文本末位不同 |
|---|---|---|---|
| playerDate_01 | 2681 | **2681/2681** | 33 |
| playerDate_02 | 2740 | **2740/2740** | 28 |
| playerDate_03 | 5777 | **5777/5777** | 29 |

**全部 double 值 100% 一致**，只有约 90 处浮点数的**末位文本表示**不同，
例如 `2.4295361042022707` vs `...705` —— 解析后是同一个 double。

**结论：无法逐字节复原，但不需要。**

受影响的只有 `GuanKaSuTongTimes`（关卡速通时间数组）和 `GuanKaJinXingTime`（关卡进行时间）——
**纯记录性数据，不参与任何数值校验。** 误差量级 1e-16 秒，游戏不可能检查。

因此验证标准定为 **结构无损**：
- 段数一致 ✅
- 每段键集合一致 ✅
- 所有 int / long / str / bool 完全相等 ✅
- float 相对误差 < 1e-12 ✅

**3 个样本档全部 PASS。**

### savedit.py 用法

```bash
python savedit.py info      <存档>                    # 查看段结构
python savedit.py roundtrip <存档>                    # 往返自测
python savedit.py get       <存档> 9.BaoShiSuiPian    # 读字段
python savedit.py set       <存档> 9.BaoShiSuiPian 9999
python savedit.py baoshi    <存档> 9999               # 宝石碎片
python savedit.py libao     <存档> 0 44               # 删除已兑码
python savedit.py pets      <存档> --level 80 --hp 99999   # 宠物属性强化
python savedit.py tree      <存档>                    # 黄金树永久
```

改文件时自动生成 `.bak` 备份。`--out FILE` 可输出到新文件。

## 七、风险分级

| 操作 | 风险 | 说明 |
|---|---|---|
| 改 `BaoShiSuiPian` | 🟢 极低 | 单整数，无统计联动 |
| 删 `LiBaoIDs` 元素 | 🟢 低 | 只影响自己的兑换记录 |
| 改 `ChongWuSiLiao` / `JinHuaShi_*` | 🟢 低 | 纯资源计数 |
| 改 `ZuanShi` / `JingYan` | 🟡 中 | 与 `NeiGouZuanShiZongShu` 等付费统计可能不一致 |
| 改 `SuoYouChongWuDate` | 🟡 中 | 派生值可能被重算 |
| 改 `GuoQiTime` / `IsHuangJin` | 🔴 高 | 涉及付费订阅，可能有日期重算 |
| 改 `IsJiHuo` / `NeiGouCiShu` | ⛔ 不建议 | 伪造付费状态，性质不同 |
| 改 `SuoYouBaoShiTongJi` | 🔴 高 | 会被 `JiSuanTongJi` 重算 |
