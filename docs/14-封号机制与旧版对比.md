## 一、三项存档修改的真机验证结果

三项需求来自「黄金树 / 宝石碎片 / 宠物」，全部在 MuMu 12 模拟器 + 真机存档上验证过。

| 项 | 字段 | 结果 | 证据 |
|---|---|---|---|
| **宝石碎片** | `seg9.BaoShiSuiPian` | ✅ **UI 实证通过** | 游戏内显示 `88888` |
| **黄金树** | `seg11.{IsJiHuo,IsHuangJin,GuoQiTime}` | ✅ **UI 实证通过** | 金色树模型 + 文字提示 |
| **宠物** | `seg6.SuoYouChongWuDate[].*` | ✅ **UI 实证通过，但触发封号** | 85 只全部 Lv60/JinHua4/JinJie10，界面显示「风冻灵主 +10」 |

### 1.1 宠物项的完整解法（最重要的一条）

宠物改档一开始只显示「**【未知型】**、等级未知、+未知」。根因是**漏写了 4 个字段**：

```json
{
  "ChongWuID": 0,
  "ChongWuLevel": 60,          ← 只写这些不够
  "ChongWuJinHua": 4,          ← 进化阶，UI 直接显示
  "ChongWuJinJie": 10,         ← 阶级
  "ChongWuYongJiu_HP": 1755000,      ← 英雄体力加成
  "ChongWuYongJiu_Damage": 1599750,  ← 英雄攻击加成
  "IsXieDai": 0,
  "IsMaoXian": -1              ← -1 = 已拥有，0 = 未拥有
}
```

**解法来源**：官方在 `data.unity3d` 里放了一个满级存档模板 `playerDate_03`（TextAsset，104886 B），
里面 `SuoYouChongWuDate` 有 **85 条真实数据**（`ChongWuID` 连续 0..84）。
全部按模板骨架重写即可 —— 见 `scripts/pet_from_template.py`。

模板的数值分布（可用于推断曲线的合理性）：

| 字段 | 分布 |
|---|---|
| `ChongWuJinHua` | `{1:49, 2:17, 3:12, 4:5, 0:2}` |
| `ChongWuJinJie` | `{10:61, 1:6, 4:4, 8:3, 3:3, 2:2, 9:2, 6:2, 0:2}` |
| `ChongWuYongJiu_HP` | 0 ~ 1755000 |
| `ChongWuYongJiu_Damage` | 0 ~ 1599750 |

`TIER_MAX = {1:(400,500), 2:(500,600), 3:(435600,277200), 4:(1755000,1599750)}`，
按 `k = 0.90 + (ID % 21)/100` 抖动，保证数值在合理的邻域内。

> **`IsMaoXian` 语义**：`-1` = 已拥有，`0` = 未拥有。游戏捕获新宠物时会写 `ChongWuJinJie = 1`。

## 二、封号机制（静态逆向，已完全搞清）

### 2.1 红屏文字

```
你的作弊行为触动了魔王的底线
魔王很生气，后果很严重
你将得到应有的惩罚！！！
忠告：请按照游戏规则进行游戏
```

**这段文字不在 metadata 里**（`惩罚`/`底线`/`忠告` 全部 0 命中），
也不在 `data.unity3d` 的可读字符串里 —— 对应 UI 槽 `XianShiNiCheng.FengHaoUI`（dump.cs 偏移 `0x40`）
的 `m_GameObject.pid = 0`，即**该槽未实例化**（prefab 模板态），运行时按服务器下发的状态才显示。

### 2.2 检测链路（反汇编确认）

```
ZuoBi.Start()                                     RVA 0x18B37B0
  ├─ if (ShuJuDate.playerZhangHao == null) return;       // 未登录不跑
  └─ StartCoroutine(JiaRuHeiMingDan(qingQiuID, playerZhangHao))
        └─ POST http://www.hqgames2013.com/heiMingDan.asp
              字段 qingQiuID + playerID
        └─ 收尾无条件执行：                          RVA 0x18B3A7C
              ShuJuDate.Init()                       0x18A7674
              ShuJuDate.BaoCunDate()                 0x18A71B4
              ShuJuDate.IsZuDang = true
              ChongWuPool.DeleteSave()               0x1857E30
              SaveManager.Clear()                    0x17A65E0
              PlayerPrefs.DeleteAll()                0x3188010
```

**关键判断**：收尾分支只判 `result == 2 (ConnectionError)` 或 `result == 3`，
**与服务器实际返回内容无关** —— 是「请求回来就清档」的形态。
这意味着**断网也救不了**（`ConnectionError` 同样走清档分支）。

### 2.3 为什么本地找不到封禁标记

清档后 `PlayerPrefs.DeleteAll()` 删掉了 key `"UJHJKOikhS"`（即 `ShuJuDate.zhangHaoKey`）里的账号名，
下次启动 `get_PlayerZhangHao()` 返回 null → `ZuoBi.Start` 里 `cbz x0` 直接 return → 不再上报，
游戏走「创建信息」新号分支。**封禁状态是服务端账号级的，本地没有任何持久化标记。**

实测验证过：

| 尝试 | 结果 |
|---|---|
| 推回设备上的原档 `SaveFile.es3.orig` | 启动显示「创建信息」新建角色界面 |
| 推回数值合法的 `SaveFile_safe.es3`（钻石 2.08万/碎片 18.2万/木材 321万，全在模板范围内） | 仍被清空成 76560 B |
| 清空 `PlayerPrefs` 的两个账号 key 绕过 `ZuoBi.Start` | 标题页时存档未动，但**登录一完成 key 就回来了**，随后 `LoadOldDate()` 触发清档 |

第三条的 logcat 铁证：

```
I Unity : PiFu:Init()
I Unity : ShuJuDate:LoadOldDate()        ← 重复十几次
```

清档由**登录成功后的读档流程**触发（`ChuangJianPlayer.DengLuChengGong()` → 写 playerZhangHao
→ `XianShiNiCheng.HeiMingDan()` 协程查 `heiMingDan.asp` → 命中则清档），与 `ZuoBi.Start` 无关。

### 2.5 结论

**封号是服务端账号级的。客户端改档一旦数值越界（或账号已被标记），下次登录就会被清档。
本地无解，唯一出路是换账号。** `scripts/safe_edit.py` 是在此之前写的「只改到模板范围内的安全编辑」
（防止数值越界被判异常），但**不解决已被标记的账号**。

### 3.1 来源与基本情况

找不到官方分发了（官网 `xiaZai.asp` 返回 `-1`，服务器在线但已停止提供下载；

实际可用来源是 [k73 游戏之家](http://www.k73.com/down/android/548432.html)，
直链 `https://k.197947.com/kdx11/android/djmw.pjb.apk`。

| 项 | 值 |
|---|---|
| 包名 | `com.HQGAMES.TopDemons`（**大写 HQGAMES**，与 TapTap 版不同） |
| versionName | `5.5.7` |
| 大小 | 86925497 B（82.89 MB） |
| SHA256 | `E6ED9D9A009E540223B702703F88B5D60EBC6577AB0B795DA93757657B397270` |

### 3.2 决定性发现：存档格式完全一致

→ **存档数据结构两版通用**，`savedit.py` / `pet_from_template.py` 等工具在旧版上可直接用。

### 3.3 加密方案差异（关键）

| 字面量 | 旧版 v5.5.7 | TapTap v5.9.2 |
|---|---|---|
| `65w84e4p994z3Oq` | **YES** | — |
| `hqgames@2013` | — | **YES** |
| `encryptionpassword` | **YES** | — |
| `PJSQJ678`（内层 DES） | YES | YES |
| `SaveFile.es3` | YES | YES |
| `AutoSave.es3` | YES | YES |
| `ES3/ES3Defaults` | YES | YES |

**两套完全不同的实现：**

- **旧版**：走 ES3 的 `ES3Settings` 默认机制，口令 **`65w84e4p994z3Oq`**
  （16 字符，位于字符串池字典序 `'6'` 与 `'7'` 之间，是 `ES3Defaults` 的 `encryptionpassword` 值）
- **TapTap 版**：没有 `encryptionpassword` 这个字面量，口令 `hqgames@2013` 直接硬编码进代码，
  通过 IL2CPP 字面量哨兵 `0xA0005EF3`（usage index 12153）引用

> TapTap 版里还有一个 `kug1oghhkt71gstktf`（18 字符，同为随机串风格），
> 可能是另一次口令生成的残留，**未验证**。

**内层 DES 两版相同**：`PJSQJ678`，`iv == key`，与 `ShuJuDate.MIMA` 常量一致。

### 3.4 账号体系

两版用**同一套 PlayerPrefs key**，但存储内容不同：

| key | 含义 | TapTap 版 | 旧版 |
|---|---|---|---|
| `UJHJKOikhS` | `zhangHaoKey` → 账号 | `o2D+pAPsvrXCo74JUkh9jw==`（防沉迷标识） | `test123%40qq.com`（**明文邮箱**） |
| `TSHYUJKSds` | `miMaKey` → 密码 | 同上（同一个值） | `abc123456`（**明文密码**） |

旧版是自有账号体系，注册页面明说「请使用自己的邮箱为账号」。
TapTap 版的 `o2D+pAPsvrXCo74JUkh9jw==` 是 **TapTap SDK 的防沉迷用户标识**（logcat 里 `anti_addict_user_identifier` 字段），
也是 ES3 桶里 string slot 的槽名（24 字符）。

### 3.5 旧版的实名弹窗（当前卡点）

旧版启动流程：

```
冷启动 → 「折相思」推广弹窗(k73 植入) → 适龄提示 → 登录/注册 → 创建信息 → 实名弹窗
```

注册后用 `test123@qq.com` / `abc123456` 登录，弹「健康游戏提示：您的账号未完成实名认证…」，
三个按钮：`切换账号` / `去实名` / `退出游戏`。**BACK 键无效**（Unity 内部绘制的强制弹窗）。

防沉迷数据存在 `/data/data/com.HQGAMES.TopDemons/shared_prefs/USER_INFO<userId>.xml`：

```json
{"userId":"test123@qq.com","identify":"","accountType":0,"onlineTime":0,
 "payMonthNum":0,"saveTimeStamp":1793266610199,"userName":"","phone":"","birthday":""}
```

**改文件无效**：把 `identify` 填成 `"1"` 或合法身份证号 `110101199001010015`、
`birthday` 填 `1990-01-01`，日志显示 SDK **确实读到了**我的值，但 `checkUserStateByLocal`
仍返回 `restrictType: 3`。判定依据不是这些字段。

### 3.6 防沉迷逻辑在 dex 里，不在 il2cpp

`checkUserStateByLocal` / `restrictType` / `identify` / `saveTimeStamp` / `getUserInfo`
在 `global-metadata.dat` 里**全部 0 命中**，但 `classes.dex`（4501188 B）里有：

```
com/antiaddiction/sdk/AntiAddictionCore        ← 主逻辑，checkUserStateByLocal 在这里
com/antiaddiction/sdk/AntiAddictionKit         ← 对外接口
com/antiaddiction/sdk/AntiAddictionPlatform    ← JNI 桥接
```

这是**国内通用的第三方 antiaddiction SDK**，不是游戏自研。
改它需要反编译 smali + 重打包，工作量大且可能破坏签名校验。

### 3.7 旧版的运行稳定性问题

```
signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x3f000000
Version '2020.3.4f1c1 (3d27070cb163)', Scripting Backend 'il2cpp', CPU 'armeabi-v7a'
ABI: 'arm', name: Job.Worker 1
```

Unity 2020.3.4f1c1 在 armv7 + Houdini（x86 模拟器翻译层）上有兼容问题，
fault addr `0x3f000000` 是浮点值被当指针/对齐错误。点击昵称输入框时会崩。

> 设备 ABI 确认：`ro.product.cpu.abilist = x86_64, arm64-v8a, x86, armeabi-v7a, armeabi`，
> armv7 可跑但**不稳**。

## 五、模拟器操作备忘（踩过的坑）

### 5.1 存档推送

`scripts/push_save.py` 封装了全部坑点：

1. `adb force-stop` 游戏
2. `adb push` 到 `/data/local/tmp/_rea_push.es3`
3. `su 0 runcon u:r:untrusted_app:s0:c42,c256,c512,c768 sh -c 'cp …'`
   —— 由游戏域自己 cp，label 自动继承 `media_rw_data_file:s0:c42,c256,c512,c768`
4. 校验 `ls -lZ` + `stat -c %s`

**顺序陷阱**：`runcon … su 10042 …` 不行（su 会重置域回 `su:s0`），
必须 `su 10042 runcon …`。

**拉回陷阱**：`su 0 cp` 出来的文件属 root，`adb pull`（shell 用户）读不到，
必须 `chown shell:shell` + `chmod 644`。

### 5.2 adb shell 引号

**`adb shell` 里 `$(...)` 不会被 PowerShell 展开，嵌套引号会被吃掉。**

```powershell
# 错：报 "Cannot execute -c"
& $adb shell su 0 sh -c "cp /a /b"
# 对：直接用命令
& $adb shell su 0 cp /a /b
# 对：要管道时用 su 0 加命令
& $adb shell su 0 head -3 /proc/1234/maps
```

`grep` 也别用 PowerShell 的 `Select-String`（`/system/bin/sh: Select-String: inaccessible or not found`）。

### 5.5 其他

- **拖地图会让游戏主线程卡死**（Unity logcat 停住、进程仍在），恢复只能 `am force-stop` + 重启
- Chrome 弹窗会抢前台：`dumpsys window | grep mCurrentFocus` 检查，需 `am force-stop com.android.chromium`
- `/storage/emulated/0/Android/data` 挂载为 `noatime`，**atime 永不变**，不能用来看游戏是否读过存档
- **frida-server 在 MuMu/Houdini 上起不来**（`exit=139` SIGSEGV），详见 [docs/08](08-模拟器翻译层调研.md)
