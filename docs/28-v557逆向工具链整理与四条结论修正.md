## 二、四个被纠正的结论

### 纠正 1：`Memory.readByteArray` 与 `ptr.readByteArray` 的方向搞反了

旧记录写的是「`ptr.readByteArray(n)` 报 not a function，要用 `Memory.readByteArray`」。
**实测正好相反**：

```
typeof Memory.readByteArray   →  'undefined'
Object.keys(Memory)           →  ['alloc', 'dup', 'patchCode', 'scan']
ptr('0x05014000').readU32()   →  '464c457f'      (0x7f454c46 = ELF magic，小端)
ptr('0x05014000').readByteArray(16)  →  ArrayBuffer ✅
```

frida 17 把 `Memory.readByteArray` / `writeByteArray` 删了，只剩 `alloc/dup/patchCode/scan`。
正确写法是 **`ptr.readByteArray(n)` / `ptr.writeByteArray(buf)`**。
判断依据不该是「报错就换个写法」，而是把 `Object.keys(Memory)` 打出来看还剩什么。

### 纠正 2：PLT 桩的判据是 `st_shndx`，不是 `st_size`

整理 `elf_v557.py` 时我先写成 `is_plt = (st_size == 4)`，跑出来 `check` 列出 46 个
「非桩」符号，size 是 8/36/816 不等 —— 一看就知道判据错了。

真实分布：

```
il2cpp_* 符号总数        232
  st_shndx == 12         232   ← 全部
    st_size == 4         186   （单指令 b #imm 跳板）
    st_size >  4          46   （带实体的跳板块，仍是导入桩）
```

**`shndx == 12` 才是桩的标志**（该段 `0x119a68`，紧挨 `.rel.plt`，全长 8768 字节）。
按 `size == 4` 判会漏掉 46 个。

### 纠正 3：v5.5.7 的 literal 索引与 v5.9.2 是两套

我一开始把 64 位版的结论直接套过来，写进注释「`0xA00039CD` = `SaveFile.es3`」。实测：

| 字符串 | v5.5.7 表项 | 64 位版（旧记录） |
|---|---|---|
| `SaveFile.es3` | **[3386]** `0xa0001a75` | 7398 |
| `PJSQJ678` | **[3089]** `0xa0001823` | 6804 |
| `hqgames@2013` | 表中**搜不到** | 12153 |
| `heiMingDan.asp` | [5647] | 5647 ✓ |

`0xA00039CD >> 1 = 7398`，而 7398 在 v5.5.7 里是「主动单体，对一个目标造成伤害…」。
所以**两个版本的 literal 表内容与下标都不同，不能互相引用**。
`encode_sentinel` 的 docstring 已标注这个方向假设在 v5.5.7 上不成立。

### 纠正 4：`libil2cpp.so` 的 `r--p` 是可复原的，但复原前要认出来

`frida_arm.py base` 首次跑出来是这样：

```
05014000-05015000 rwxp  off=0x0        ← 我上一轮 Memory.protect 改的
05212000-05213000 r-xp  off=0x1fe000   ← 同上
052cd000-0618c000 r--p  off=0x2b9000   ← 12.7MB 代码主体，仍是 r--
0618c000-0618d000 rwxp  off=0x1178000  ← 同上
```

如果只看这份输出，很容易得出「代码段是可执行的，inline hook 应该可行」的错误结论 ——
但这些 `x` 是**探测脚本自己改出来的**，不是进程原始状态。

→ 教训：**任何读 `/proc/<pid>/maps` 的工具都要说明「这是当前状态，可能被之前的探测改过」**。
脚本里 `arm_maps()` 的 docstring 已加这条警告。要拿原始状态，重启游戏进程再看。

## 三、frida 能力矩阵（`frida_arm.py probe` 可完整复现）

| 能力 | 结果 | 证据 |
|---|---|---|
| 读 ARM 段内存 | ✅ | `read 0x05014000 16` → `7f 45 4c 46 01 01 01 00 ...` |
| `Memory.protect(...,'rwx')` | ✅ | 前后 `Process.findRangeByAddress` 权限从 `r--` 变 `rwx`，进程存活 |
| 写 ARM 代码并读回 | ✅ | 见下 |
| `Interceptor.attach` ARM 地址 | ❌ | 见下 |
| x86→ARM 调用桥 | ❌ | `libhoudini.so` 62 个导出全是 `NativeBridgeItf` / `android_*` |

**写入实证**（`write 0x0618c800`）：

```
before  : 43 97 01 81 b0 ab 80 80 00 00 00 00 43 97 01 81
after   : 00 00 a0 e1 00 00 a0 e1 00 00 a0 e1 1e ff 2f e1
          ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ mov r0,r0 ×3 + bx lr
restored: 43 97 01 81 b0 ab 80 80 00 00 00 00 43 97 01 81
```

**Hook 失败实证**（`hook 0x052ccb50`，即 il2cpp 段首函数）：

```
before  : 10 4c 2d e9 08 b0 8d e2 44 00 9f e5 00 00 9f e7
after   : 10 4c 2d e9 08 b0 8d e2 44 00 9f e5 00 00 9f e7
attached: True    changed: False    hits: 0
```

`attached` 返回 true、`detach` 也不崩，但机器码**一字节都没被改写**，回调 `hits` 恒 0。
这说明 Interceptor 的插桩对象是 x86 侧的代码缓存，而不是 Houdini 翻译前的 ARM 原始段。

**结论：能看数据，不能动代码。** 这与 docs/27 的判断一致，但现在有了可复现命令。

## 四、哨兵表位置（顺带确认）

可写段 `0x061c9000` 全长 `0x77000` 扫下来 **7046 个** `0xA0000000|(idx<<1)|1` 形态的哨兵，
首个在 `0x6210ef8`（即段起 `+0x7ef8`）。

- 段开头 0x2000 字节**一个都没有** —— 早期「从段起扫」会误判成全零表
- 7046 vs 早前记的 7052，差 6，属运行期表项变化，量级吻合
- `frida_arm.py sentinel <addr> <size>` 的 size 必须覆盖到 `+0x7ef8` 之后

## 六、踩坑清单

| 现象 | 真因 |
|---|---|
| `'not a function'`（读内存时） | frida 17 删了 `Memory.readByteArray`，要用 `ptr.readByteArray` |
| `ReferenceError: hex is not defined` | `hex()` 在 frida 17 脚本里不是全局函数，用 `ptr.toString()` |
| 扫到的地址全部 `access violation` | `Memory.scanSync` 的 `match.address` **已是绝对地址**，再 `.add(base)` 就越界 |
| 哨兵扫描 0 命中 | 用 `>>` 而不是 `>>>`；超过 `0x7FFFFFFF` 会做有符号转换而永假 |
| `attach` 报 `ProcessNotFoundError` | pid 是旧的。先 `ps -A \| grep` 拿最新 pid，别断定 frida 不可用 |
| `struct.error: requires buffer of N bytes` | ELF32 头是 `<IIHHHH` 六个值，少写一个 `H` 就会读错偏移 |
| capstone 只解出极少数指令 | `il2cpp` 段中间有合法编码空洞，必须 `md.skipdata = True` |
| 段表解析「看起来能跑但全是垃圾」 | 步长错。`TypeDefinition` 是 `0x58` 不是 `0x5C`；`MethodDefinition` 是 `0x20` 不是 `0x2C`；`FieldDefinition` 是 `12` 不是 `0x10` |

## 七、对后续的影响

1. **静态分析链路现在完整可复现**：metadata → 类/方法/字段 → ELF 符号 → 真实地址。
   以后查任何类不用再写一次性探针。
2. **动态分析的天花板已经钉死**：Houdini 下只能读，不能 hook、不能调用 ARM 函数。
   想要「调一下 `GameGUI.OpenChongWuUI()` 看看宠物界面」，在当前环境无解 ——
   这条已经两次撞墙，不必再试第三次。
3. **v5.5.7 与 v5.9.2 的常量要分开记**。literal 索引、存档格式、DES 填充规则
   全都不一样，混用会得到「解析成功但内容错位」这种最难查的 bug。
