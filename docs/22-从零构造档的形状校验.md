# 22 - 从零构造档的形状校验（第一层 + 第二层）

> 这一篇是 docs/21（`new_save.py` / `edit_seg2510.py`）的**验证篇**。
> 起因：用户问「后续如何测试」。回答分四层，本文覆盖前两层 ——
> 不需要模拟器、不需要设备，只验「产出的字节在游戏眼里的形状对不对」。

## 一、为什么"能解开"不等于"能读"

仓库早先的测试都停在「我们的库能解回来」。但游戏读档走的是 ES3 的
反序列化路径，它对**字段是否齐全**是有要求的：

- 它按 key 名去 JSON 里取，取不到就落默认值（不报错）；
- 但「少了应当有的 key」在业务层可能被当成数据损坏。

所以真正的判据不是「能解开」，而是 **形状和游戏自己写的档一致**。

## 二、发现：唯一满级模板是「旧版本遗留」

`evidence/templates/` 有 3 份官方 TextAsset：

| 模板 | seg12 字段数 | seg13 字段数 | seg2 |
|---|---|---|---|
| `playerDate_01.bin`（36 级） | **14** | 22 | 18（无 `ZiYuanLiXianTime`） |
| `playerDate_02.bin`（56 级） | **14** | 22 | 18（无 `ZiYuanLiXianTime`） |
| `playerDate_03.bin`（60 级） | **27** | 29 | 19 |
| 真机 `device_orig.es3` | **31** | 29 | 19 |
| 游戏回写 `after_orig.es3` | **31** | 29 | 19 |

`tools/template_diff.py` 的完整输出（以真机档为基准）：

```

                              'TanPai_ZCS','TanPai_ZJF','TanPai_ZQCS']
```

**结论**：`playerDate_01/02` 是旧版本（14 段格式尚未定型）遗留，不能当基准；
`playerDate_03` 最接近但**仍缺 seg12 的 4 个 `TanPai_*`**。

`Date_FuLiLevel`（`dump.cs:263386`，TypeDefIndex 3076）共 31 个字段，
末尾正是这 4 个 + 5 个 `TanPai_*`：


文件名 `playerDate_03` 里带 "03" 也可能暗示它是第 3 次导出的资源，
不是版本号 —— 但无论哪种解释，**缺字段这个事实都要处理**。

## 三、修法：`new_save.py` 增加字段补全

新增两个候选表 + 两个函数：

```python
SHAPE_REFERENCE_CANDIDATES = (
    "evidence/saves/SaveFile_device_orig.es3",
    "evidence/saves/SaveFile_after_orig.es3",
)

def load_reference(explicit=None):   # -> ([14 段], path) | None
def merge_reference(segs, ref):      # 返回被补的字段名列表
```

`merge_reference` **只补不改**：

- 模板已有的字段值一律保留（模板是满级档，值是设计好的）
- 缺的字段按参考档里的相对位置插入，维持与真机档一致的字段顺序
- 插入策略：在参考档里找该字段之后最近一个「模板里也有」的字段当锚点，
  插到它前面；后面没有锚点则追加到末尾

命令行新增两个开关：

| 开关 | 作用 |
|---|---|
| `--reference PATH` | 指定参考档（默认自动找） |
| `--no-merge` | 关掉补全，用模板原样（形状会和真机档不一致） |

实测输出：

```
[merge] 从 SaveFile_device_orig.es3 补齐 4 个字段:
        seg12.TanPai_IOP, seg12.TanPai_ZCS, seg12.TanPai_DTCS, seg12.TanPai_CZT
[out ] work\live\_merge_test.es3 (210528 字节)
自检   : 通过
```

## 四、第一层：离线自检回归 `tools/test_new_save.py`

不依赖设备。6 组、38 条断言：

| 组 | 验什么 |
|---|---|
| [1] 外层与桶形状 | `salt`/`iv` 复用原档、桶不以 `{` 开头、条目名与顺序与真档一致、string 槽名 == 账号名 |
| [2] `--set` 精确改写 | 段数不变、每段字段集合不变、目标字段确实改了、**只有 seg0/seg13 有差异** |
| [3] 解包/封包往返 | 零改动重封 == 原档（逐字节） |
| [4] 交叉验证 | 与游戏自己回写的 `after_orig.es3` 逐段比字段集合 |
| [5] 负例 | `--no-merge` 必须真的缺那 4 个 `TanPai_*`，否则 [4] 是假绿 |
| [6] `edit_seg2510` 形状保持 | 只动 seg2/seg5/10、salt/iv/桶条目不变、seg5 宝箱全开 |

[5] 是刻意加的**反证组**：如果哪天 [4] 通过了但补全逻辑其实没生效
（比如模板被换成了新版），[5] 会先失败，提示「这条负例的前提已变」。

运行：

```bash
python tools/test_new_save.py
# -> ALL PASS
```

## 五、第二层：交叉验证取证脚本 `tools/cross_check_shape.py`

断言版只说 PASS/FAIL；这个脚本把每项差异打全，用于换模板/换参考档后人工核对。

它比三样东西：

1. **14 段字段集合**（与 `after_orig.es3` 比）
2. **桶条目名 + 类型序列**（`_Key` long、账号名 string、7 个 `*ShuChu_Key` long）
3. **外层 salt/iv 的来源**（必须来自 `device_orig`，不是随机）

**输出里有两个"不一致"是预期内的，不要误判**：

- `salt 一致: False` —— 基准档 `after_orig` 是游戏回写时换了新的随机 salt；
  我们按 docs/19 复用 `device_orig` 的 salt。所以脚本真正检查的是
  `salt/iv 来自 SaveFile_device_orig.es3: True`。
- `文件大小 76944 vs 210528` —— 模板是满级档（内层 104959 字节），
  基准是新手档（内层 ~76 KB）。值不同是设计使然。

最终判定：

```
形状一致：14 段字段集合、桶条目名与类型、外层 salt/iv 来源全部符合
（值不同是预期的：模板是满级档，基准是新手档）
```

## 六、这两层证明了什么 / 没证明什么

**证明了**：

- 生成的档在外层加密参数上与真机一致（不会触发 docs/19 的黑屏条件）
- 桶结构（槽名 = 账号名、`_Key`、7 个计数器）与游戏自己写的完全一致
- 14 段的字段集合与游戏实跑后写的档**完全一致**（补全后）
- 解包再封包逐字节无损，没有隐藏的归一化
- `edit_seg2510` 的改动范围是可控的（只碰 seg2/5/10）

**没证明**：

- 游戏实际运行时接不接受（需要设备 + 可用账号，见 docs/14 封号问题）
- 字段**取值**是否落在业务允许的范围内（模板都是官方满级值，风险较低；
  但 `--set` 任意的值没有校验）
- `_Key`（2640 vs 4224）是否影响读档 —— 目前照抄原档，未做对照实验
