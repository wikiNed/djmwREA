## 一、存档格式

```
{json0}${json1}$...${json13}
```

- **14 段独立 JSON 对象**，用 `$` 字符拼接
- 每段自带 `DateID` 字段（0~13），**段号可靠，不依赖数组下标**
- UTF-8 编码，**无 BOM**（个别文件开头有 BOM，读取时需 `utf-8-sig`）
- **无加密、无压缩、无 HMAC、无 CRC、无签名**

### 各段含义

| DateID | 内容 |
|---|---|
| 6 | 宠物数据 `SuoYouChongWuDate`、各类进化石、饲料 |
| 9 | 宝石洞 `BaoShiSuiPian` 宝石碎片 |
| 11 | 生命树/黄金树 `GuoQiTime` 等 |
| 13 | 礼包码 `LiBaoIDs` 已兑换列表 |

## 二、往返安全性（2026-10 重新实测）

### 结论：安全

| 存档 | 数字 token 总数 | 数值完全等价 | 文本末位不同 |
|---|---|---|---|
| playerDate_01 | 2681 | **2681/2681** | 33 |
| playerDate_02 | 2740 | **2740/2740** | 28 |
| playerDate_03 | 5777 | **5777/5777** | 29 |

**全部数字的 double 值 100% 一致**，只有约 90 处浮点数的**末位文本表示**不同：

```
游戏原文        2.4295361042022707
工具重存        2.4295361042022705     ← float() 解析后是同一个 double
```

因为存档没有任何校验机制，游戏读档时 `float()` / `double.Parse()` 得到完全相同的值，
**所以文本差异不影响游戏，可以安全写回。**

### 浮点格式化：已试过但不成立的假设

记录在此以免重复踩坑：

| 假设 | 复原率 | 结论 |
|---|---|---|
| Python `repr()`（shortest round-trip） | 66~75% | 否 |
| .NET `ToString()` 最短表示 | 90/123 | 否 |
| double 的精确十进制展开 `Decimal(float)` | 2/123 | 否，游戏值明显更短 |
| `ROUND_DOWN`（向零）@17 位 | 6/123 | 否，错得离谱 |
| `ROUND_CEILING` @17 位 | 82/123 | 否，比 HALF_UP 更差 |
| `ROUND_HALF_UP` @17 位（当前采用） | **90/123** | 最接近，保留 |

> **判断**：反推游戏确切浮点算法的边际收益极低。文本差异不影响数值、
> 不影响游戏运行。除非有证据表明游戏会校验存档文本，否则不值得继续追。

#### 为什么必须重算段 9 统计

`SuoYouBaoShiTongJi`（`dump.cs:263285` `BaoShiTongJi`）里 13 个字段与宝石数组一一对应：

| 字段 | 口径 | 依据 |
|---|---|---|
| `baoShiShuJie_01..07` | 按品阶计数，`Jie_0N` = `PinJie N-1` | 03 档：33 颗 PinJie=6 ↔ Jie_07=105（历史累计） |
| `baoShiShu_PuTong..YuanGu` | 按稀有度计数，与枚举同名 | 03 档 `YuanGu` = 3 = 当前 XiYouDu=5 的 3 颗，完全吻合 |
| `baoShiZongShu` | **历史累计**获得总数 | 03 档 23812 远超当前持有 497 |
| `baoShiShu_FenJie` | 历史累计分解数 | 21884，无法从当前状态推导 |

**所以只改宝石数组、不改统计，会留下"有 497 颗远古但统计说只有 3 颗"的矛盾状态。**
`baoshiall` 默认会同步重算能确定的 13 项（品阶 7 + 品质 6），
`ZongShu` / `FenJie` 属历史累计量，保持原值（仅当当前总数更大时才抬高 `ZongShu`）。

#### 为什么不新增宝石

`baoShiID` 的编码规则未破译（样本 ID 1003~24812，与颜色/品阶的映射未知），
且 `isZhuangBei` / `zhuangBeiID` 必须与 `HeroZhuangBeis[].XiangQianBaoShiID` 严格对应。
随意插入会造出"宝石声称镶在 X，但装备 X 的孔位里没有它"的不一致状态。
**因此只强化已有宝石，不增删数组。**

**这里必须纠正一个常见误解。**

`SuoYouChongWuDate` **不是"已获得的宠物列表"，而是全部 85 种宠物的属性表。**

证据：三份官方演示存档里 85 个槽位**全部有值**，`ChongWuLevel` 最低也是 1。
`dump.cs:263195` 的 `ChongWuDate` 只有 8 个字段，**没有任何"是否拥有"标志**：

```csharp
public class ChongWuDate // TypeDefIndex: 3066
{
    public uint  ChongWuID;              // 0x10
    public uint  ChongWuLevel;           // 0x14   等级
    public uint  ChongWuJinHua;          // 0x18   进化阶段 0~4
    public uint  ChongWuJinJie;          // 0x1C   阶级
    public ulong ChongWuYongJiu_HP;      // 0x20   永久生命
    public ulong ChongWuYongJiu_Damage;  // 0x28   永久攻击
    public uint  IsXieDai;               // 0x30   是否携带（同时只能 1 只 = 1）
    public int   IsMaoXian;              // 0x34   是否冒险
}
```

**所以：在存档层无法"获取"宠物，因为宠物本来就全在表里。**

能改的是**属性**。真正的"开放"是解锁宠物**玩法**，
对应运行时方法 `ChongWuPool.OpenAllChongWu()`（`dump.cs:256215`）。

```bash
python savedit.py pets <archive> --level 80 --jinhua 4 --jinjie 10 \
                                --hp 99999 --dmg 99999 --out out.json
```

实测：

```

受影响段: [6]  字段: ['SuoYouChongWuDate']
样例: ID0 Level 20 -> 80 | HP 150 -> 99999
```

注意实现是 `max(原值, 目标值)`，**只上调不下调**，避免把已培养的宠物改低。

### C. 黄金树永久（段 11）

**先纠正一个错误认知**：早期判断"黄金由 `GuoQiTime` 推导"是错的。

三份官方存档横向对比给出了决定性证据：

| 存档 | IsJiHuo | IsHuangJin | GuoQiTime |
|---|---|---|---|
| playerDate_01 | 1 | **1** | 2020-07-12（早已过期） |
| playerDate_02 | 1 | **1** | 2020-07-08（早已过期） |
| playerDate_03 | 0 | **0** | 2020-07-05 |

**01/02 的树在 2020 年就过期了，`IsHuangJin` 却仍然是 1。**
所以"黄金"是**独立保存的等级标志**，不是由到期时间算出来的。

`dump.cs:263367` 的 `Date_ShengMingShu`（TypeDefIndex 3075）完整字段：

```csharp
public class Date_ShengMingShu
{
    public uint  DateID;              // 0x10
    public uint  IsJiHuo;             // 0x14   激活标志
    public uint  IsHuangJin;          // 0x18   黄金等级标志 ← 关键
    public ulong GuoQiTime;           // 0x20   到期时间戳(毫秒，注意是 ulong)
    public uint  JiHuoCiShu;          // 0x28   累计激活次数
    public uint  GuoShiIsLingQu;      // 0x2C   果实是否已领
    public ulong GuoShiChongZhiTime;  // 0x30   果实重置时间戳
}
```

**结论：把 `IsHuangJin` 置 1、`IsJiHuo` 置 1、`GuoQiTime` 推到远期，
即可同时满足"是黄金"和"不过期"两个条件。**

```bash
python savedit.py tree <archive> --out out.json
```

实测（基于 playerDate_03，原状态 `IsJiHuo=0 IsHuangJin=0`）：

## 六、仍需在真机验证的部分

四项操作（宝石 / 宠物属性 / 黄金树 / LiBaoIDs）在**工具层已全部实测通过**，
格式、字段、写入、回读全部可复现。但**改完之后游戏是否买账**仍缺一环：

1. **真实存档位置**——游戏用 **ES3（Easy Save 3）** 存储（见文档 05），

2. 若走 ES3，需要 hook `SaveManager.Save<T>` / `Load<T>` 确认 key 映射
3. 改完是否需要重新登录 / 触发保存才生效

**这三条都需要 adb + 真机，当前环境不具备。**

另外需要说明：游戏侧可能对这些标志做二次校验（例如登录时向服务端
核对 `IsHuangJin`）。若要绕过，属于服务端协议层面，
需要抓包分析 `UpHuangJinShu` 接口，同样依赖真机。
