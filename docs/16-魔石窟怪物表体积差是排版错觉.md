# 16 — 魔石窟怪物表：48KB 体积差是个假象

> **更新**：2026-10-29
> **前情**：[docs/14 §3.2](14-封号机制与旧版对比.md) 的 TextAsset 对照表里，
> `MoShiKuGuaiDate` 一栏是 `87282 → 39005`，标着「只有 45%」，列为未解疑点。
> **本文结论**：那个 45% 是**排版差异**的错觉。内容上只多了 2 只怪，
> 其余 25 只逐字段相同（仅技能名大小写规则变了）。

---

## 一、先给结论

| 项目 | TapTap v5.9.2 | 旧版 v5.5.7 |
|---|---|---|
| 文件大小 | 87282 B | 39005 B |
| JSON 顶层 | `{"shengWu": [...]}` | 同左 |
| 怪物数 | **27** | **25** |
| ID 范围 | 0..122（跳号） | 0..120 |
| 字段集 | 10 个，与旧版**完全相同** | 同左 |
| 同 ID 内容差异 | 25 只全部只在 `JiNengs[].JiNengStr` 的大小写上 |

**体积差 48277 B 里，只有 6759 B 是真实内容增量。** 其余 4 万多字节是缩进。

---

## 二、排版差异怎么造成的

两份文件开头就不同：

```
新版: EF BB BF  7B 0A 20 20 20 20 22 73 68 65 6E 67 57 75 22 3A 20 5B
      BOM       {  \n ␣␣␣␣  "  s  h  e  n  g  W  u  "  :  ␣  [
      → {"shengWu": [

旧版: EF BB BF  7B 0A 20 20 20 20 22 73 68 65 6E 67 57 75 22 3A 0A
      BOM       {  \n ␣␣␣␣  "  s  h  e  n  g  W  u  "  :  \n
      → {"shengWu":
             [
```

旧版把 `[` 换行缩进了，新版没有。用同一种格式化重排两边：

| 格式化方式 | 新版 | 旧版 | 差 |
|---|---|---|---|
| 原文件 | 87279 | 39002 | 48277 |
| `indent=4` | 87278 | 80519 | **6759** |
| `indent=2` | 56866 | 52475 | 4391 |
| 紧凑（无空格） | 25050 | 23131 | 1919 |

**`indent=4` 重排后旧版从 39002 涨到 80519** —— 可见 39002 那个数字根本不是
「旧版内容只有一半」，而是「旧版用了另一种缩进密度」。

> **教训**：比 JSON 文件大小时，先规范化再比。
> 否则比较的是 `indent` 参数，不是内容。

## 三、真实的内容增量：2 只新怪

| ID | Name | HP（三档） | Damage（三档） | 说明 |
|---|---|---|---|---|
| 121 | **小光** | 8,000,000 / 16,000,000 / 1,600,000,000 | 70,000 / 140,000 / 200,000 | ★ 新增 |
| 122 | **小暗** | 20,000,000 / 40,000,000 / 4,000,000,000 | 50,000 / 100,000 / 150,000 | ★ 新增 |

两只都是「魔石窟里的稀有宠物，打败它有几率会成为你的宠物」，
`JingHuaConst` 都是 `[6, 18, 36]`。

技能配置：

| | 小光 | 小暗 |
|---|---|---|
| 1 档（CD 6） | `MengJi` | `Sleep_DanTi` |
| 2 档（CD 5） | `MengJi` | `Sleep_DanTi` |
| 3 档（CD 3） | `MengJi` + `JiGuangYan` | `Sleep_All` + `HunLuan_All` |

掉落（三档，概率随档位递增 `0.002/0.003/0.004` 掉宠物）：

```
['MoShiSuiPian', 'ChongWu', 'ZuanShi', 'SiLiao', 'MoWuSuiPian']
数量 [2, 86 或 87, 1, 1, 1/3/6]
概率 [0.2, 0.002~0.004, 0.5, 0.9, 1]
```

注意 `ChongWu` 那一项的掉落数量是 **86 / 87** —— 正好接上
`playerDate_03` 模板里 85 只宠物（ID 0..84）的编号。
也就是说这两只怪的 ID 121/122 与宠物 ID 86/87 是两个独立编号体系，
不要混。

## 四、那 25 只共有怪到底差在哪

只有一个字段：`JiNengs[].JiNengStr` 的**大小写**。

```
新版 ID=0  JiNengStr: ['Wu']       × 3
旧版 ID=0  JiNengStr: ['wu']       × 3
```

全部 24 个技能名都遵循同一规律：

| 新版（大驼峰） | 旧版（首字母小写） |
|---|---|
| `BingShuang` | `bingShuang` |
| `DaHuoQiu` | `daHuoQiu` |
| `DiZhen_All` | `diZhen_All` |
| `DuWu_DanTi` | `duWu_DanTi` |
| `HunLuan_All` | `hunLuan_All` |
| `JiGuangYan` | `jiGuangYan` |
| `Sleep_DanTi` | `sleep_DanTi` |
| `Wu` | `wu` |
| …（共 24 个，全部） | |

**忽略大小写后，两版技能名集合完全相同**（各 24 个，对称差为空）。

这与 `dump.cs` 里的枚举定义一致：

```csharp
public enum JiNeng // TypeDefIndex: 3176
{
    public const JiNeng Wu = 34;
    public const JiNeng BingShuang = 36;
    public const JiNeng JiSu = 38;
    public const JiNeng MengJi = 44;
    public const JiNeng ZhaoHuanKuLou = 50;
    public const JiNeng ShiHua = 52;
    public const JiNeng TouQie = 53;
    public const JiNeng JiGuangYan = 54;
    …
}
```

枚举成员名本来就是大驼峰。**新版是「向枚举命名规范对齐」，旧版是历史遗留的不规范写法。**

### 4.1 这个大小写会不会有影响

需要确认游戏是按字符串查表还是按枚举解析。查了两条路径：

1. **`Enum.Parse` 根本没被调用** —— 扫 `.text` 全部 798500 条指令，
   `Enum.Parse(Type, string)` @ `0x292AE48` 与三参重载 @ `0x292AEB0`
   **0 处调用**。所以 `JiNengStr` 不走 `Enum.Parse`。

2. **技能名的显示用的是 `ToString()`** —— `GetJiNengXinXi.JiNengName(JiNeng j)` @ `0x18D9A68`：
   ```
   0x18D9B00: bl #0x292d980   ; -> Enum.ToString()
   0x18D9B14: bl #0x27776b8   ; -> String.Concat(string, string)   拼上本地化前缀
   0x18D9B28: bl #0x17a49f0   ; -> string GetLanguageText(string key)
   ```
   即：**`j.ToString()` 得到枚举成员名（大驼峰），拼前缀后作为本地化 key**。

   `GetLanguageText` @ `0x17A49F0` 按语言枚举 `switch`（`[x20,#0x10]` 取值 0..4），
   一路走到 `0x17A4A94 bl #0x278057c ; string op_Equality(string,string)` 做字典匹配；
   默认分支 `0x17A4C78` 直接从单例取字段返回（兜底，不比对）。

   这条链用的是**枚举名**，与 JSON 里写的字符串没关系。

**结论**：`JiNengStr` 是数据侧的显示/查询键，不是枚举解析入口。
两版都能跑；新版统一成大驼峰只是规范化。如果自造魔石窟怪物表，
**建议跟新版一样用大驼峰**，因为 `JiNeng` 枚举就是这么命名的。

## 五、新增怪在代码里怎么被用

`MoShiKuManager.GetMoWuDate(int id)` @ `0x18BC680` 是查表入口：

```
0x18BC6C8:  ldr  x8, [x20, #0x28]!     ; shengWuDate
0x18BC738:  ldr  w10, [x8, #0x18]      ; 数组长度
0x18BC750:  add  x11, x8, w9, sxtw #3  ; 第 i 个元素
0x18BC75C:  ldr  w12, [x11, #0x10]     ; 元素的 ID 字段
0x18BC764:  cmp  w12, w19              ; == 请求的 id？
0x18BC768:  csel x0, x11, x0, eq       ; 命中就保存
```

纯线性扫描按 `ID` 字段匹配。所以**往表里加条目，只要 ID 不重复就天然被支持**，
不需要改任何代码或索引结构。

`MoShiKuGuaiWu.get_JiNeng()` @ `0x18B92B0` 则从 `[x0,#0x148]` 的 `JiNeng[]` 里
随机抽一个（`0x18B92C8 bl #0x318845c ; Random.Range`），
这就是魔石窟怪物「随机放技能」的实现。

## 六、这对改档有什么意义

1. **不需要为旧版单独准备怪物表** —— 两版字段完全一致，只有技能名大小写不同。
2. **改档不受影响** —— `MoShiKuGuaiDate` 是 TextAsset，不在存档里
   （存档 14 段中与魔石窟相关的是 `DateID=10`，字段是 `MoGaoLevel` / `MoShiShuLiang` /
   `MoKuNanDuDangQian` / `MoKuTiLi` 等**进度**，不是怪物表）。
3. **想让旧版也认新版表** —— 直接把 87282 那份的 `shengWu` 拼到旧版 JSON 里即可，
   字段名一一对应。反过来把旧版的给新版也能读，只是技能名是小写。

## 八、一句话总结

**「旧版怪物表只有 45% 大小」是个排版错觉 —— 规范化之后只差 6759 字节，
内容是多了 2 只怪（小光 / 小暗，ID 121/122），其余 25 只逐字段相同，
唯一差别是技能名从 `wu` 改成了 `Wu`。**
