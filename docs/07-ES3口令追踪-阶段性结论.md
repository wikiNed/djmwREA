## 三、静态槽 `0x35e7408` 的解析结果（已追到尽头）

### 重定位表（section 9，RELA，375336 条；section 10，575 条）
```
r_offset = 0x35e7408   type = 1027 (R_AARCH64_RELATIVE)   addend = 0x36F5DB0
```
即加载时 `*(0x35e7408) = base + 0x36F5DB0`。

### 但 `0x36F5DB0` 处（文件 offset `0x36e9db0`）的内容
```
d3 44 00 a0 00 00 00 00   d5 44 00 a0 00 00 00 00   d7 44 00 a0 00 00 00 00 ...
→ 一串递增 8 的指针，值域 0xA00044xxxx
```

### 文件里 `0x35e7000` 整个区域**全零**（512 字节内 0 个非零字节）

### 运行时实际读取（`/proc/PID/mem`，`bs=1` 精确 seek）
```
0x35e7408 在 maps 段 0a778000 (file off 0x341c000) 内
runtime = 0x0a778000 + (0x35e7408 - 0x3424000) = 0x0a93b408

读 0x0a93b408:  0x000000000aa50618
读 0x0aa50618:  0x00007d396adcba40  0x00000000a0005ef5  0x00000000a0005ef7 ...
```

`0xA0005EF5` 这类值在之前 `frida_slot2.py` 的 dump 里也出现过（`f75e00a000000000`），
**高 16 位 `0xA000` 是 MuMu ARM 翻译层对 guest 内存的标记**，不是可用的绝对地址。

**结论：这一串值不是 `Il2CppString*`，`0x35e7408` 也不是直接的 password 字段槽。**
最可能是 `il2cpp_class_init` 的「静态字段区起源指针」表，真正的 password 字符串在
初始化函数运行时才被构造并填入。

## 四、`.so` 的 vaddr 与 file offset **不相等**（重要坑）

ELF program headers（`e_phoff=0x40`, 10 项）：

| idx | Offset | vaddr | filesz | flags |
|---|---|---|---|---|
| 1 | `0x0` | `0x0` | `0x1432aec` | R-- |
| 2 | `0x1432aec` | `0x1436aec` | `0x1fe97f4` | **R-X** |
| 3 | `0x341c2e0` | `0x34242e0` | `0x21dbb0` | RW- |
| 4 | `0x3639e90` | `0x3645e90` | `0x218008` | RW- |

- 段 2：`vaddr - offset = 0x4000`
- 段 3：`vaddr - offset = 0x8000`

**换算公式：`feoff = vaddr - p_vaddr + p_offset`，必须按段分别算。**
早期脚本假设 `RVA == file offset`，因此 `dump.cs` 给的 RVA 会读错位置。

## 六、frida 在 MuMu 翻译层下的硬限制（有 tombstone 证据）

崩溃记录 `/sdcard/Android/data/game.taptap.HQGAMES.TapDemons/files/tombstone_00`：

```
signal 4 (SIGILL), code 0 (SI_USER)
pc  0000000008b1b720        ← 被 hook 的地址（ES3Writer.Create）
lr  0000000008e422d4
backtrace:
  #00 pc 000000000174b720    libil2cpp.so   ← RVA 0x174B720 == ES3Writer.Create
  #01 pc 0000000001a722d0    libil2cpp.so   ← 紧邻 ES3.Save<object> @0x1A722C8
  #02 pc 00000000018a7634    libil2cpp.so   ← ShuJuDate.Init 尾部
  #03 pc 00000000018a710c    libil2cpp.so   ← ShuJuDate.SaveGame 附近
```

**backtrace 打印的是 RVA，不是绝对地址。** 由此反推：

```
base = 0x08b1b720 - 0x174b720 = 0x073D0000
```

`0x073D0000` 才是正确 load base（中途一度怀疑的 `0x07354000`、`0x7d3964715000` 都是错的）。

**但 hook 仍然不可用**：`libil2cpp.so` 的主体代码段在 maps 里是

```
08b1c000-08e3f000 r--p 017c4000    ← 只读、不可执行
```

MuMu 把 ARM 代码当**数据**喂给翻译层，CPU 从不直接执行 ARM 指令。因此 frida 的
inline hook（写 ARM 指令）**没有执行机会**；上次写进 4KB 的 `r-xp` stub 区后直接 SIGILL。

**且段地址在运行中会整片迁移**（观测到 `0x07354000` 与 `0x7d3965fbd000` 两套映射并存），
任何写死的 base 都会失效。

→ **要在运行时 hook，必须用真机 ARM64 或支持 ARM 直跑的模拟器实例。**
