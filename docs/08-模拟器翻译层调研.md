# MuMu 12 ARM 翻译层调研 — Houdini 分析

> 目的：判断能否在 MuMu 12（x86_64 引擎）上对 ARM64 的 IL2CPP 游戏做 frida hook。
> 结论：**不能。已穷尽探查。**

---

## 一、模拟器引擎情况

```
MuMuPlayer 5.27.4.3536
实例标签        120.2.161.006-nemux-default-x64-release
engine          nemux
```

`MuMuManager setting -v 0 -a` 列出的全部设置项中，**没有任何 `arch` / `abi` / `engine` / `arm` 切换项**。

MuMu 12 的 `x64-release` 是该产品唯一提供的引擎，**不存在纯 ARM 实例模式**。

---

## 二、翻译层组件（实测 maps）

```
/system/lib64/libhoudini.so             Intel Houdini，ARM→x86 翻译器
/system/lib64/arm64/nb/libtcb.so        Houdini translator control block
/system/lib64/libnb.so                  MuMu 包装（导出 NativeBridgeItf @ 0x7d3a35947740）
/system/lib64/libnemuinitaidl.so        AIDL 接口
/system/lib64/libnblog.so               日志
```

Houdini 导出 145 项，其中 `ibt_get_version` @ `0x7d3a21bec9f0`、`ibt_get_expire_date`。
其地址空间基准 `0x7d3a2164c000`。

---

## 三、Houdini 的 code cache（唯一可写可执行区域）

`Process.enumerateRanges('rwx')` 实测 4 段：

```
0xd4da000        size      73728   rwx
0xd4ec000        size   65454080   rwx   ← 主 code cache（62 MB）
0x11358000       size      16384   rwx
0x7d3cdde3c000   size      73728   rwx
```

**这是唯一能在 x86 侧安全写入 inline hook 的区域**（其余 ARM 代码段是 `r--p`，写就崩）。

### 在其中搜索 ARM 源地址常量
把 `0x08b1b720`（ES3Writer.Create）、`0x08866d44`（AES.Encrypt）、`0x0988c7e0`（PBKDF2 ctor）、
`0x08b4e374`（ShuJuDate.LoadGame）按 32 位小端和 64 位两种形式扫全 62 MB：

```
cc_scan (32-bit)  : writer=0  aes=0  kdf=0  loadgame=0
cc_scan64 (64-bit): writer=0  aes=0  kdf=0  loadgame=0
```

**零命中** → Houdini 的 TB 表用哈希索引，不存明文源地址；
或表位于 `libtcb.so` 的 `rw` 段（`0x0d4af000-0x0d4d8000`）内，布局无公开文档。

## 四、两套地址空间的真相

同一个 `libil2cpp.so` 在进程里有**两套并行映射**：

**低地址（Android 常规加载，ARM guest 视图）**
```
07354000 r--p 00000000   file off 0x0        ELF 头
0878a000 r--p 01432000
08b14000 r-xp 017bc000   4KB stub
08b1b000 r-xp 017c3000   4KB stub   ← 0x174B720 在这里
08b1c000 r--p 017c4000   ARM 主体代码（不可执行！）
0a778000 r--p 0341c000   .data/RW 视图
0a999000 rw-p 03639000   .data
```

**高地址（Houdini 给 guest 的另一份，生命周期不稳定）**
```
7d3964715000 r--p 00000000
7d3965e59000 r-xp 01744000
7d3965fbc000 r-xp 018a7000
...
```
切后台再回来后，这整片会消失或迁移。

## 五、base 到底是多少（由 tombstone 定案）

崩溃记录 `tombstone_00`：
```
signal 4 (SIGILL), code 0 (SI_USER)
pc  0000000008b1b720
lr  0000000008e422d4
backtrace:
  #00 pc 000000000174b720   ← RVA 0x174B720 == ES3Writer.Create
  #01 pc 0000000001a722d0   ← 紧邻 ES3.Save<object> @0x1A722C8
  #02 pc 00000000018a7634   ← ShuJuDate.Init 尾部
  #03 pc 00000000018a710c   ← ShuJuDate.SaveGame 附近
```

**backtrace 打印的是 RVA。** 于是：

```
base = 0x08b1b720 - 0x174b720 = 0x073D0000
```

**`0x073D0000` 是正确 load base。** 中途怀疑的 `0x07354000`（ELF 头段起点）与
`0x7d3964715000`（Houdini 高地址视图）都不是。

**但即使 base 正确，hook 依然不可行** —— 因为目标段是 `r--p`，
写入它触发的是翻译层元数据破坏 → SIGILL。

## 六、能做的和不能做的

| 能力 | MuMu x86 翻译层 | 真机 ARM64 |
|---|---|---|
| 读进程内存（`/proc/PID/mem`，root） | 可用 | 可用 |
| dump 堆找明文 | 可用（但实测零命中，见下） | 可用 |
| frida `Interceptor.attach` ARM 函数 | SIGILL | 可用 |
| frida hook 导出函数（libc `open` 等） | 可装，但游戏走 ARM 侧不经此处 | 可用 |
| 静态反汇编 / 修改 `.so` | 可用 | 可用 |
| 写回加密存档 | 缺口令 | 缺口令（除非 hook 到） |

### 内存搜明文也失败（实测）
- dump 2071 个 `rw` 段的全部大块 → `DateID` / `SaveFile` / `BaoShiSuiPian` **零命中**
- 在切后台（触发 `YanShiTime=6` 存档）的窗口内做 40 轮 burst 扫描 → **零命中**

**推断：ES3 用流式 `CopyStream(input, cryptoStream)` 写盘，完整 JSON 从不在堆上成形；
且 `SaveFile.es3` 路径字符串由原生层拼接，不以 UTF-8/UTF-16 明文驻留。**

---

## 七、可行出路（按成本排序）

1. **真机 ARM64**（任意 Android 手机 + USB 调试）：`base + RVA` 直接可用，
   hook 一次即拿到口令。**成本最低、成功率最高。**
2. **官方 Android Studio ARM64 AVD**：需下载 ~8-10 GB（SDK + arm64 system image）。
   但 x86 主机上是 **qemu 全模拟、无硬件加速**，Unity 3D 游戏大概率跑不起来。
3. **静态挖 il2cpp 初始化函数**：纯静态、无需设备。需要扩展 `find_slot_writers.py`
   识别"间接写入"形态（`str xN, [xM]`，其中 `xM` 由前序计算）。工作量大，无 frida 反馈，盲搜。
4. **接受现状**：四项改动的工具与文档已完备，只是无法写回加密的真实存档。
