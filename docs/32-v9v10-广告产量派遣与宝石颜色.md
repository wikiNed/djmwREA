## 2. v9 四项改动

### 2.1 广告奖励 80 次、永不计次

`class GuangGaoCiShu`（字段 `guangGaoCiShu //0x10`，`private const int guangGaoShangXian = 20`）：

| VA | 原值 → 新值 | 含义 |
|---|---|---|
| `0xEE4064` | `A9BF7BFD` → `52800A00` | `GetGuangGaoShangXian` 改为 `mov w0,#80` |
| `0xEE4068` | `910003FD` → `D65F03C0` | 紧随其后的 `RET` |
| `0xEE4090` | `A9BE4FF4` → `52800020` | `AddCiShu` 改为 `mov w0,#1`（永远"成功"、不累加） |
| `0xEE4094` | `A9017BFD` → `D65F03C0` | `RET` |
| `0xEE4054` | `B9401000` → `52800000` | `get_GuangGaoDangQianCiShu` 恒返回 0（已看次数永远 0，剩余恒 80） |

原实现里 `AddCiShu` 会先比 `used >= max`，超了返回 0；现在直接返回 1，且写入路径被 `RET` 截断。

### 2.2 木材 50 万/秒、矿石 30 万/秒

v8 是两边各 50,000/s，v9 把木提到 50 万、矿提到 30 万。**注意 300000 塞不进 `movz` 的 16 位立即数**
（上限 65535），所以这里用的是 `movz + lsl` 两步凑数：

| VA | 原值 → 新值 | 含义 |
|---|---|---|
| `0xEBF9D0` | `1B137D08` → `D28F4240` | 木：`movz x0, #0x7A12`（31250） |
| `0xEBF9D4` | `93407D00` → `D37CEC00` | 木：`lsl x0, x0, #4` ⇒ 31250×16 = **500,000** |
| `0xEC0550` | `1B137D08` → `D28927C0` | 矿：`movz x0, #0x493E`（18750） |
| `0xEC0554` | `93407D00` → `D37CEC00` | 矿：`lsl x0, x0, #4` ⇒ 18750×16 = **300,000** |
| `0xEBFA54` | `1E210800` → `1E2E1000` | 木：结算间隔 `fmul` → `fmov s0,#1.0` |
| `0xEC057C` | `1E210800` → `1E2E1000` | 矿：同上 |

> 改速度只要改「movz 的立即数 × 16」；要 100,000/s 就 `#0x186A`（6250×16），
> `mov w8,#imm` 也一样能用（imm ≤ 65535），机器码 = `0x52800000 | (imm<<5) | Rd`。

**实测**：把存档里木/矿与离线库全部置 0，重进游戏，35 秒内木 5,364,060、矿 3,660,540 直接满仓。
按 50,000/s 需要 107 秒，所以实际速率确实是十万量级以上。

### 2.3 宝石六色等概率

`ShenQiBaoShiDateModel::RandomYanSeBaoShi @0xEB64A8` 原本按权重数组
`private float[] baoShiZhongLeiDiaoLuo; // 0xD8` 抽颜色（数组序列化在场景资源里，改字节不如直接改函数）。

整段函数改写成：

```
bl   0x735BB8          ; Random.value / Range(0,1)，参数沿用原函数的 (s0=0, s1=1, x0=0)
mov  w9, #6
...                    ; ×6 -> fcvtzs -> cmp 5 -> csel 钳位
ret
```

结果：返回 `0..5` 均匀分布，六种颜色各 **1/6 ≈ 16.7%**。

### 2.4 派遣 3 秒（v9 的写法是错的）

v9 改的是 `MoShiKuManager.get_PaiQianNeedTime @0x8C5F5C`（**魔王库**派遣的时长），
招募/派遣大厅（`ZhaoMuManager`）根本不走它，所以界面上还是一小时。正确改法见第 3 节。

## 3. v10：派遣时长真正改成 3 秒

### 3.1 真实公式

在 `ZhaoMuManager.SetWuZiAndText`（`0xE405B8`）里：

```
0xE413F0  ldr  s8, [x8, #0x20]     ; 单场耗时（配置数组，按难度索引）
0xE41404  bl   0xEC4CD4            ; get_PaiQianTime() = 5.0 或 20.0
0xE41408  ldr  s1, [x19, #0x58]    ; 次数 ciShu
0xE41410  ldr  s2, [0xFDDD8C]      ; = 60.0（下限）
0xE41414  fmul s0, s8, s0          ; 单场 × PaiQianTime
0xE41418  scvtf s1, s1             ; 次数转 float
0xE4141C  fmul s0, s0, s1          ; × 次数
0xE41420  fmax s0, s0, s2          ; 至少 60 秒
0xE41424  str  s0, [x19, #0xB8]    ; paiQianTime 字段
```

代入截图里的「第 43 关、刷 50 次」：`3.6 × 20 × 50 = 3600 s`，正好 1 小时。
外层还有 `fmax(…, 60)`，所以**只把 20 改小也顶不掉 60 秒下限**。

### 3.2 补丁

把 `0xE41408 ~ 0xE41420` 七条指令整段替换成「直接写 3.0」：

| VA | 原值 | 新值 | 说明 |
|---|---|---|---|
| `0xE41408` | `BD405A61` | `52880008` | `movz w8, #0x4000` |
| `0xE4140C` | `90000CE8` | `72A80808` | `movk w8, #0x4040, lsl #16` → w8 = `0x40400000` = 3.0f |
| `0xE41410` | `BD4D8D02` | `1E270100` | `fmov s0, w8` |
| `0xE41414` | `1E200900` | `D503201F` | NOP（原 fmul） |
| `0xE41418` | `5E21D821` | `D503201F` | NOP（原 scvtf） |
| `0xE4141C` | `1E210800` | `D503201F` | NOP（原 fmul 次数） |
| `0xE41420` | `1E224800` | `D503201F` | NOP（原 fmax 60.0） |

`0xE41424` 的 `str s0, [x19, #0xB8]` 保留，于是 `paiQianTime` 恒为 3.0，
后面的 `SetPaiQianTimes(Time + 3)` 也就写在 3 秒后。**与关卡、难度、次数全部无关。**

脚本：`scripts/patch_v10_paiqian.py`（逐条校验原值，不匹配就退出）。

## 3.5 v11：宝石升级成功率下限 75%

`ShenQiBaoShiDateModel.GetLevelUpChengGongLv(ShenQiBaoShiClass baoShi) @0xEB6A6C`：
按宝石稀有度（`baoShi + 0x24`，0..5）走跳表（表基 `0xFDE93C`），各分支给出基础成功率，
最后统一走同一段收尾：

```
0xEB6BB8  mov x1, xzr
0xEB6BBC  bl  0xED2E70          ; 取加成
0xEB6BC0  ldp x29, x30, ...
0xEB6BC4  ldp x20, x19, ...
0xEB6BC8  ldr x21, [sp, #8]
0xEB6BCC  fadd s0, s8, s0       ; 基础 + 加成
0xEB6BD0  fmov s1, #1.0
0xEB6BD4  fmin s0, s0, s1       ; 上限 1.0
0xEB6BD8  ldr d8, [sp], #0x30
0xEB6BDC  ret
```

只改最后两条即可，**下限 75%、高于 75% 的保持原值**：

| VA | 原值 → 新值 | 含义 |
|---|---|---|
| `0xEB6BD0` | `1E2E1001` → `1E2D1001` | `fmov s1, #1.0` → `fmov s1, #0.75` |
| `0xEB6BD4` | `1E215800` → `1E214800` | `fmin s0, s0, s1` → `fmax s0, s0, s1` |

> 两个机器码都用 capstone 反解验证过：`1e2d1001` = `fmov s1, #0.75000000`，
> `1e214800` = `fmax s0, s0, s1`。
>
> **副作用**：原来那条 1.0 的上限被这条 fmax 顶掉了。由于基础值取自跳表（本身 ≤1.0）、
> 加成来自 `0xED2E70`，正常不会超过 1.0；万一显示成 100%+，表现是必成功，不影响功能。

脚本：`scripts/patch_v11_gemupgrade.py`。

## 3.6 v12：升级成功率 90% + 升级消耗 ÷10

### 成功率 90%（`0xEB6BD0`）

v11 用的是 `fmov s1,#0.75`（VFP 立即数能表示 0.75）。**0.9 表示不了**——
VFP 立即数只支持 `±(16+m)/16 × 2^e`，0.9 对应 `16+m = 14.4`，不是整数。
全库只有一份 0.9f（`0x3F666666`）在 **VA `0xF4A2BC`**，于是改成 PC 相对加载：

| VA | 原值 → 新值 | 含义 |
|---|---|---|
| `0xEB6BD0` | `1E2D1001` → `1C49B761` | `ldr s1, [pc, #0x936EC]`（指向 `0xF4A2BC` 的 0.9f） |

`0xEB6BD4` 的 `fmax s0,s0,s1` 保持不动 ⇒ 返回 `max(原值, 0.9)`。

### 升级消耗 ÷10（两份副本）

`GetLevelUpSuiPianShu @0xEB681C` 里同一段收尾**写了两遍**（`0xEB6A34` 与 `0xEB690C` 各一份），
原型是把基础数转 float、乘 `(1 - 折扣)`。两处都改成直接乘 0.1：

| VA（两份各 4 条） | 新值 | 含义 |
|---|---|---|
| `+0x00` | `9E230260` | `ucvtf s0, x19`（基础数 → float） |
| `+0x04` | `529999A8` | `movz w8, #0xCCCD` |
| `+0x08` | `72A7B988` | `movk w8, #0x3DCC, lsl #16` ⇒ w8 = `0x3DCCCCCD` = 0.1f |
| `+0x0C` | `1E270101` | `fmov s1, w8` |

之后原有的 `fmul s0, s0, s1` 就把结果变成 **基础数 × 0.1**（折扣不再参与）。
两份地址分别是 `0xEB6A34`、`0xEB690C`。

> 注意 `0xEB6A44` 是 `ldp x29,x30,[sp,#0x20]` 收尾，**不能动**。

## 3.7 v13：欧气/非气恒 50 + 神秘商店库存不减

### 欧气 / 非气（v12 改错对象的教训）

v12 改的是 `get_OuQiShuLiang @0xE5F420` / `get_FeiQiShuLiang @0xE5F428`，
但界面显示的是「8/199」——它**直接读字段** `ouQiShuLiang //0x150`、`feiQiShuLiang //0x154`
（199 = `private const int qiTiShuMax = 199`），根本不走 getter，所以完全没反应。

v13 改成在 `LoadOuQiFeiQi @0xE5F430` 里把两个字段直接写成 50，并让 `Add*` 不再累加：

| VA | 原值 → 新值 | 含义 |
|---|---|---|
| `0xE5F430` | `A9BE4FF4` → `52800648` | `mov w8, #0x32`（50） |
| `0xE5F434` | `A9017BFD` → `B9015008` | `str w8, [x0, #0x150]`（欧气） |
| `0xE5F438` | `910043FD` → `B9015408` | `str w8, [x0, #0x154]`（非气） |
| `0xE5F43C` | `D0003194` → `D65F03C0` | `ret` |
| `0xE5F4B4` | `A9BE4FF4` → `D65F03C0` | `AddOuQiShu` → `ret`（原实现里有 `mov w9,#0xC7` 的 199 上限） |
| `0xE5F5B0` | `A9BE4FF4` → `D65F03C0` | `AddFeiQiShu` → `ret` |

配合 v12 已把 `RemoveOuQiShu @0xE5F534`、`RemoveFeiQiShu @0xE5F630` 改成 `ret`，
结果就是**恒为 50，既不涨也不掉**。

### 神秘商店库存

v12 只把 `RemoveKuCun @0xEB0F3C` 改成「永远返回成功」，但 `kuCun` 字段本身早就被买空了，
所以满屏缺货——这是**存量**问题。v13 在 `LoadKuCun @0xEB0C74` 里每次把库存重置成上限：

| VA | 原值 → 新值 | 含义 |
|---|---|---|
| `0xEB0C74` | `A9BE4FF4` → `B9403008` | `ldr w8, [x0, #0x30]`（`kuCunMax`） |
| `0xEB0C78` | `A9017BFD` → `B9002C08` | `str w8, [x0, #0x2c]`（`kuCun`） |
| `0xEB0C7C` | `910043FD` → `D65F03C0` | `ret` |

配合 `RemoveKuCun` 恒成功 ⇒ 每次进商店/重进游戏都是满库存，买完不减。

### 教训

**Unity IL2CPP 里「字段」和「属性 getter」是两条路**。改之前要先确认 UI 到底走哪条：
本项目的 UI 大量直接读字段（这次欧气就是），改 getter 等于没改。
判断方法：把 getter 改成返回常量，看界面变不变；不变就说明走字段，得去改**赋值处**（加载/累加函数）。

## 5. 真机验证记录（Huawei P30 / ELE-AL00 / Android 10 / 1080×2340）

- **存档迁移**：从 Honor（v8）拉出 `djmw@163.com`（117,503 B），改 `ZhangHao` 为目标机的存档名后推入，

- **派遣**：v10 装好后用户确认 3 秒生效。

### 真机上的几个坑（与模拟器不同）

1. **uiautomator 的 bounds 与真实像素有约 +235px 的纵向偏移**（实名弹窗实测），
   而且 `bounds` 属性排在 `resource-id` 之前，按「rid 后接 bounds」解析会取到下一个节点。
   定位一律以 OCR/像素剖面为准。
2. **`adb shell input text` 输入中文无效**（华为 IME 吞非 ASCII），必须用 ADBKeyboard：
   `ime set com.android.adbkeyboard/.AdbIME` → `am broadcast -a ADB_INPUT_B64 --es msg <base64>` →
   用完 `ime set com.baidu.input_huawei/.ImeService` 还原。
3. 登录页（1080×2340）：账号 y984 / 密码 y1152 / 验证码 y1320 / 登陆 `(540,1476)`；
   每段输完先点 `(540,790)` 收键盘（键盘会遮住验证码框）。
4. 创角页：昵称框 y1340-1440、「进入游戏」`(540,1555)`（点两次）。
5. **建筑等级必须配人口**：存档里写 `240/299/245` 但人口只写 9，游戏读档后会把整段 `seg2` 重置为 0。

## 6. 待办 / 已知未尽事项

- 64 位补丁表里**没有**平移 32 位那 8 条反作弊（只做了 `ZuoBi.Start→RET` 与 `QingDang→RET` 兜底），
  **37 天封号闸仍未在 64 位上堵**（`ShengMingZhiShuUI.Update` 那条）。
- v9 里对 `MoShiKuManager.get_PaiQianNeedTime` 的改动保留着（魔王库派遣也变成 3 秒），无害。
- 派遣的"单场耗时"数组、以及 `get_PaiQianTime()` 的 5/20 两个值仍保留原样，只是不再参与计算。
- 广告次数改的是 `GuangGaoCiShu` 全局上限；如果某个玩法有自己单独的次数校验，需要另找。
