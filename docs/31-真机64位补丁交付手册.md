## 四、36 条补丁（权威表在 `scripts/build_patched_lib64.py` 的 `PATCHES`）

`RET = 0xD65F03C0`（`ret`），`NOP = 0xD503201F`。地址是**手机 64 位 lib 的 VA**（也是文件偏移，该 lib 的 `.text`/`il2cpp` 段 va==off）。

### 4.1 资源 50000/s（严格 50000，不靠随机）

| VA | 原字 → 新字 | 含义 |
|---|---|---|
| `0xEBF9D0` | `1B137D08 → 52986A08` | 木材产额 `mul w8,w8,w19` → `mov w8,#0xC350`（50000） |
| `0xEC0550` | 同上 | 矿石产额 |
| `0xEBFA54` | `1E210800 → 1E2E1000` | 木材间隔 `fmul` → `fmov s0,#1.0` |
| `0xEC057C` | 同上 | 矿石间隔 |

想改别的速度只动前两行：`mov w8,#imm` 的机器码 = `0x52800000 | (imm<<5) | 8`
（10000→`5284E208`，50000→`52986A08`），**改完务必用 `chkwords.py` 让 capstone 复核**。

实测（v8，`MuCaiShuLiang`/`KuangShiShuLiang` 先置 100,000）：38 秒后两者都是
**2,000,000**（+1,900,000 ≈ 50,000/s），存档级 ground truth，不是截图读数。
v7（10000/s）时代离线 781 秒 → 781.00 万，木/矿约 9 分钟顶满（536.41 万 / 360.15 万）；
50,000/s 下从 0 到顶满约 **107 秒**（木材）/ **72 秒**（矿石）。

### 4.2 宝石分解 ×100（4 处显示 + 12 处一键分解）

`GetFenJieSuiPianShu` 在 64 位被内联，所以「单个分解」和「一键分解的 6 个稀有度分支」要分别改：

| VA | 原字 → 新字 | 含义 |
|---|---|---|
| `0xEB6BF8` / `0xEB6C00` | `D341FC08→D2800648` / `9A9F1500→9B087C00` | 单个分解**显示** `raw/2 → raw*50` |
| `0xEB947C` / `0xEB9484` | `D341FC08→D2800648` / `9A9F1501→9B087C01` | 分解**到账** `raw/2 → raw*50` |
| `0xEB6E00/08`、`0xEB6FD0/D8`、`0xEB71A0/A8`、`0xEB7370/78`、`0xEB7540/48`、`0xEB7710/18` | 同上两条 | 一键分解 6 档的**总数显示** |

> 到账上限在 `AddBaoShiSuiPian @0xEB8C58`：当前碎片 > 99,999,998 才拒绝，所以正常玩不会撞顶。

### 4.3 钻石 / 肉 / 草丛「只增不减」

| VA | 原字 → 新字 | 含义 |
|---|---|---|
| `0xE557F0` | `F81D0FF5 → RET` | `RemoveZuanShi` 整体返回（花钻石不扣） |
| `0xE5EB34` | `A9BE4FF4 → RET` | `RemoveSiLiao` 整体返回（肉不扣，HUD 恒 597/597） |
| `0xED9B24` | `A9BE4FF4 → RET` | `AddCiShu` 整体返回（今日抓宠次数不增，草丛恒 9/9） |

> **纪律**：只能在「扣减函数」里做「不扣」，**不要**在扣款路径里把余额写大——
> 那会命中 `0xe55850 b.ge #0xe558d0` 的异常分支，直接弹作弊红屏（v4 的教训）。

### 4.4 战斗/概率

| VA | 原字 → 新字 | 含义 |
|---|---|---|
| `0xFDDD88` | `BDCCCCCD → BC23D70A` | 进下层衰减 `-0.1f → -0.01f`（全库只有 1 处引用） |
| `0xEF5D68` | `00000000 → 3EDB6DB7` | 自造 `3/7` 常量（塞进 `.rodata` 的零填充空位） |
| `0xEB6150` | `1E2703E0 → 1C1FE0C0` | 远古池 `fmov s0,wzr` → `ldr s0,#0xef5d68` |
| `0xEB61D8` | `1E232800 → 1E2CD000` | 远古阈值 `fadd → fmov s0,#0.6875` |
| `0xEB61DC` | `1E242800 → 1E200900` | 远古阈值 `fadd → fmul s0,s8,s0`（合起来：远古恒 31.25%） |
| `0xDF4118` | `11000508 → NOP` | 洞穴界面的探秘次数自增 |
| `0xDF3CD4` | `5400058A → NOP` | 洞穴次数上限判定 `b.ge` |

> 后两条合起来 = 探秘次数在界面上恒为上限（实测恒 60）。

### 4.5 反作弊 / 启动 / 登录

| VA | 原字 → 新字 | 含义 |
|---|---|---|
| `0x406D9C` | `39412800 → 52800000` | **nullfix**：重签包启动时的空指针 |
| `0xE0C7A0` | `A9BE4FF4 → RET` | `ZuoBi.Start` → 封号协程不启动 |
| `0xECAE10` | `F81E0FF3 → RET` | `ShuJuDate.QingDang` → 永不删档 |
| `0xEB5730` | `A9BE4FF4 → RET` | `AddBaoShiDongTiLi` → 模型侧次数不增 |
| `0xE15304` | `140000A8 → 14000010` | 登录：响应 `"0"`（服务器对所有账号的答复）→ 走进成功体 `0xE15344` |
| `0xE15100` | `370000C0 → 14000091` | 登录：网络错误分支 → 同样进成功体 |

> 登录绕过的原理：`GetYongHuQingQiu.MoveNext @0xE14EA4` 用 FNV-1a 把响应文本
> 哈希后 switch，只有 `"111"`(`0x6C361B12`) 是真成功。服务器现在对任何账号都回 `0`，
> 所以把 `"0"` 分支直接跳到 `0xE15344`（111 成功体的真正主体）。

### 4.6 32 位版为什么「看起来更简单」

32 位补丁表在 `scripts/build_patched_apk.py` 的 `WORDS`（含反作弊的 `PlayerPrefs.DeleteAll`、
`ChongWuPool.DeleteSave`、`FengHaoUI.SetActive`、`HeiMingDan` 判定、37 天闸等 8 条）。
64 位**没有**逐条平移那 8 条，理由：`ZuoBi.Start → ret` 已把整条封号协程掐死在入口，
协程体内的删档/弹窗不可达；`QingDang → ret` 再兜一层。**唯一还没堵的是 37 天闸**（见 §7）。

## 五、存档：格式、改法、字段

### 5.1 格式（v5.5.7 是**单层** DES，别套 TapTap 版的 AES 双层）

```
file  = header(14 字节) || hex_upper( DES-CBC-PKCS7(明文) ) || b"{"      # 末尾一个 '{'
key = iv = b"PJSQJ678"                                                  # == ShuJuDate.MIMA
明文  = 14 段 JSON，用 "$" 连接
```

- 密文是**大写十六进制文本**，不是二进制，所以直接看文件也能认出边界。
- 内层必须 PKCS7 填充（早期用 NUL 填充 → 游戏报 `Bad PKCS7 padding` 卡标题页，见 [docs/13](13-内层DES填充与卡死根因.md)）。
- TapTap 版（v5.9.2，`game.taptap.HQGAMES.TapDemons`）才是「外层 AES-128-CBC(PBKDF2 `hqgames@2013`) + 内层 DES」，
  那套的 salt/iv 必须复用原档（[docs/19](19-改档黑屏根因-salt与iv必须复用.md)）。**两个版本的加密不是一回事。**

### 5.2 改档（唯一推荐姿势）

```powershell
# 改字段（段号.字段名=值，可多个）；二进制段原样保留，不重新生成
& $py scripts\tools64\setsave.py in.save out.save "13.ZuanShi=50000" "6.ChongWuSiLiao=597"
# 拆段看内容
& $py scripts\v557save.py dump in.save outdir
```

`v557save.read_segments(path)` 返回 **`(header, [bytes]*14)` 元组**，段是 bytes（可能非 UTF-8），
不要当 list 用、不要无脑 `decode("utf-8")`。

### 5.3 各段速查（v5.5.7）

| 段 | 内容 | 常用字段 |
|---|---|---|
| 0 | 玩家 | `PlayerName`、`TapLevel`、`TapZongShu` |
| 1 / 6 | 英雄 / 宠物 | 体积大，别乱动 |
| 6 | 宠物日期 | `ChongWuSiLiao`（肉）、`DangTianZhuaChongShu`（今日已抓，草丛 = 9 − 它）、`ZhuaChongZongShu`、`CaoCongChongZhiTime` |
| 8 | 关卡 | `GuanKaLevel` |
| 10 | 魔石/宝石 | `MoGaoLevel`（上限 = ×100）、`MoShiShuLiang`、`MoWuSuiPian`、`BaoShiSuiPian` |
| 11 | 生命之树 | `IsJiHuo`、`IsHuangJin`、`GuoQiTime` |
| 13 | 账号/货币 | `ZuanShi`、`JingYan`、`ZhangHao`、`WeiYiMa`、`LianJiBest` |

> **草丛不在存档里**：它是「9 − 今日已抓次数」算出来的。存档只有 `DangTianZhuaChongShu`。
> **肉在存档里**：`ChongWuSiLiao`（默认上限 300，界面显示的 597 是升级后的动态上限）。

### 5.4 推档到手机

```powershell
& $adb -s $s shell am force-stop com.HQGAMES.TopDemons
& $adb -s $s push v7_base.save "/sdcard/Android/data/com.HQGAMES.TopDemons/files/djmw@163.com"
& $adb -s $s shell am start --user 0 -n com.HQGAMES.TopDemons/com.unity3d.player.UnityPlayerActivity
```

- 存档文件名 = **账号名**（当前 `djmw@163.com`），二进制内不含账号字符串。
- 手机有两个用户，`am start` 必须带 `--user 0`，否则 `SecurityException`。
- 拉回来核对字段是唯一可靠的验收方式（截图 OCR 会丢位）。

## 十、踩过的坑（浓缩版）

1. **64 位代码不在 `.text`**：`il2cpp` 段从 `0x4af1e0` 起，所有 `0xexxxxx` 地址都在这里。
2. **64 位没有尾部字面量池**：32 位的 `vldr s0,[pc,#0x200]` 在 64 位是 `fmov s0,wzr` 或 `adrp+ldr`，
   必须按语义对照，不能按函数内偏移硬平移。
3. **`fmov` 立即数不是线性编码**：`0x1E2CD000`=0.6875、`0x1E2C9000`=0.625、`0x1E2CF000`=0.71875，
   手算必错，用 capstone 反查。
4. **`mul x0,x0,x8` = `0x9B087C00`**（MADD 的 Rm 在 bit[20:16]），不是 `0x9B107C00`。
5. **索引对齐靠 metadata 直接算**：两版 `global-metadata.dat` 版本都是 27，模块基址都是 26588，
   所以 `methodPtr 索引 = 全局方法索引 − 26588`，锚点三处验证过。
6. **`bl` 调用点反查比全库扫偏移有效**：想找「扣饲料的地方」，从 `bl RemoveSiLiao` 反着找同簇方法，
   比扫 `str w?,[x?,#0x34]`（4510 个命中）快一个数量级。
7. **作弊判定盯的是「余额上升」**：对扣款函数做 `ret` 是安全的，把它改成「写大值」会立刻红屏。
8. **沙箱里 git 不稳**，二进制只用 Python 读写，绝不用 PowerShell 重定向。
