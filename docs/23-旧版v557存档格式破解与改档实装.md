## 二、实名弹窗绕过（旧版的第一个门槛）

启动后卡在「健康游戏提示 / 您的账号未完成实名认证」，点任何按钮都只能退出。

### 定位过程

`global-metadata.dat` 里 `checkUserStateByLocal` / `restrictType` **全部 0 命中** ——
防沉迷不是 C# 代码，是第三方 Java SDK：

```
com/antiaddiction/sdk/AntiAddictionCore
com/antiaddiction/sdk/AntiAddictionKit
com/antiaddiction/sdk/AntiAddictionPlatform
```

用自写的 dex 反汇编器 `tools/dex_disasm.py` 找到真正判定点：
`Lcom/antiaddiction/sdk/service/PlayLogService;->checkUserStateByLocal(User;Z)Lorg/json/JSONObject;`

关键分支（`code_off=2072432`）：

```smali
0048  const/4  v2, #3      ; v2 = 3（目标 restrictType）
004c  if-gtz  v6, +5       ; v6 <= 0 跳到 0x0056
0050  const/4  v6, #0
0052  const/4  v4, #3      ; restrictType = 3（未实名受限）
0054  goto   +15
```

`v6 > 0` 时判定为未实名。实测该值来自 `saveTimeStamp`。

### 解法

`/data/data/com.HQGAMES.TopDemons/shared_prefs/USER_INFO<账号>.xml`：

```xml
"onlineTime":0,"payMonthNum":0,"saveTimeStamp":1793266610199,"userName":"",
"phone":"","birthday":""}</string>
```

把 `saveTimeStamp` 改成 `0`：**弹窗消失，直接进「创建信息」。**

> 之前尝试填 `identify`（合法身份证号）、`birthday`、`phone` 全部无效 —— 判定不看这些字段。

## 三、存档文件格式（与 TapTap 版完全不同）

### 定位

建完角色后存档生成在
`/storage/emulated/0/Android/data/com.HQGAMES.TopDemons/files/test123@qq.com`
（**文件名是账号名**，不是 `SaveFile.es3`），75167 字节。

### 格式

```
file = header(14 字节) || hex_upper( DES-CBC-PKCS7(明文) ) || b"{"
header = 7e 00 99 25 01 00 ff ee f1 e9 fd 90 cb 04
```

- 外层 DES-CBC，**key == iv == `b"PJSQJ678"`**
- 无内层（TapTap 版是 AES-128-CBC 外层 + DES 内层）
- 尾部 1 字节 `{`（0x7B）
- 明文 14 段，用 `$` 分隔

### 与 TapTap 版完整对照

| | 旧版 v5.5.7 | TapTap 版 v5.9.2 |
|---|---|---|
| 文件 | `test123@qq.com` 75167 B | `SaveFile.es3` 76976 B |
| 外层 | **DES-CBC**，key=iv=`PJSQJ678`，hex 大写包裹 | AES-128-CBC，PBKDF2(`hqgames@2013`,salt,100,16) |
| 内层 | **无** | DES-CBC，key=iv=`PJSQJ678` |
| 头 | 14 字节 | 16 salt + 16 IV |
| 尾 | `{` (0x7B) | 无 |
| 存档框架 | Easy Save **2**（`ES2Settings`） | Easy Save **3**（`ES3`） |
| 段数/分隔 | 14 / `$` | 14 / `$` |

### 破解过程中的三个坑

1. **头部不是纯 hex**：前 14 字节是二进制，其中第 14、15 字节 `0x36 0x32`（ASCII `"62"`）
   恰好也是合法 hex 字符，导致最早切分时多吞了 14 个字符。真正的 hex 段是 75152 字符 = 37576 字节。
2. **没有独立 IV**：整个 body 都是密文，IV 就是 key。
3. **密码不是 `hqgames@2013`**：旧版 metadata 里这个字符串 count=0。
   穷举后确认是 `PJSQJ678`（与 `ShuJuDate.MIMA` 常量一致）。

## 四、header 长度编码（本阶段最难的一关）

### 现象

只要明文长度改变，游戏就报：

```
CryptographicException: Bad PKCS7 padding. Invalid length 74.
FormatException: Could not find any parsable digits.
  at System.ParseNumbers.StringToInt
  at ShuJuDate.DesDecrypt (System.String DecryptText, System.String sKey)
  at ShuJuDate.LoadGame ()
```

### 根因

`DesDecrypt @ 0x7C1E38` 反汇编显示它**只接收 text 和 sKey，header 完全不参与解密**。
那 header 为什么会影响？因为它记录**长度**。

让游戏自己写一次档（拉回来 75231 字节），对比：

```
原档   75167  头 7e 00 99 25 01 00 ff ee f1 e9 fd 90 cb 04
回写   75231  头 7e 00 d9 25 01 00 ff ee f1 e9 fd d0 cb 04
变化：         [2] 0x99→0xD9        [11] 0x90→0xD0     （均 +0x40 = +64）
```

**delta = 64，两处各自 +64。**

### 解码规则

```
header[2]  = (0x99 + delta) & 0xFF     ← 长度低字节
header[11] = (0x90 + delta) & 0xFF     ← 同一个长度的另一份拷贝
header[3]、header[12] 恒为 0x25、0xCB  ← 不是长度高字节
```

**两条硬约束：**

1. **`header[3]` 必须恒为 `0x25`，`header[12]` 必须恒为 `0xCB`** —— 之前误以为是 16 位小端高字节，
   按小端进位算出来的头全部失败。
2. **`header[2]` / `header[11]` 是单字节长度，只能加不能进位。**
   上限 = `0xFF - 0x99 = 0x66 = 102`。

### delta 边界实测

| 实际 delta | h[2] | h[3] | h[11] | h[12] | 结果 |
|---|---|---|---|---|---|
| 0 | 0x99 | 0x25 | 0x90 | 0xcb | ✅ |
| 16 | 0xa9 | 0x25 | 0xa0 | 0xcb | ✅ |
| 32 | 0xb9 | 0x25 | 0xb0 | 0xcb | ✅ |
| 64 | 0xd9 | 0x25 | 0xd0 | 0xcb | ✅ |
| 80 | 0xe9 | 0x25 | 0xe0 | 0xcb | ✅ |
| **96** | **0xf9** | **0x25** | **0xf0** | **0xcb** | **✅ 上限** |
| 112 | 0x09 | 0x26 | 0x00 | 0xcc | ❌ |
| 128 | 0x19 | 0x26 | 0x10 | 0xcc | ❌ |
| 256 | 0x99 | 0x26 | 0x90 | 0xcc | ❌ |
| 1072 | 0xc9 | 0x29 | 0xc0 | 0xcf | ❌ |

**负 delta 也合法**：`header[2] = (0x99 + delta) & 0xFF`。
用 `seg8` 里 123 个哨兵浮点 `1000000000.0`（16 字节）替换成 `0.0`（3 字符），
每个省 9 字节明文 → delta −16 实测成功。

### 实现

`scripts/v557save.py`：

```python
BASE_TOTAL = 75167
HDR_LEN_POS = (2, 11)

def fix_header_length(header, total_len):
    hdr = bytearray(header)
    delta = total_len - BASE_TOTAL
    if delta == 0:
        return bytes(hdr)
    for p in HDR_LEN_POS:
        v = (hdr[p] + delta) & 0xFF
        hdr[p] = v
    return bytes(hdr)
```

> 注意：**必须基于纯净基准头 `7e0099250100ffeef1e9fd90cb04` 计算**。
> 如果传入的 header 已经含长度信息，再用 `BASE_TOTAL` 作基准会重复累加。

## 八、新增工具

### `tools/dex_disasm.py`（391 行）

自写 dex 反汇编器。`androguard disassemble` 的 offset 是 `code_item` 结构体偏移
（需 +16 才是指令），且 `get_instructions()` 在 4.1.4 返回空，故自写。

```
Dex 类：strings / type_name / field_ref / method_ref / iter_methods / code_bytes
OPS 表：opcode → (助记符, 格式)
decode(dex, code) → [(addr, mnemonic, operand_str), ...]
code_bytes(code_off) → (bytes, regs, ins, insns)   # 跳过 16 字节 code_item 头
```

用法：`python tools/dex_disasm.py <dex> <类描述符> [方法名...]`

> **踩坑：dex 文件头 `0x38` 处是 12 个 u32 而不是 10 个**，
> 少读两个会导致 `ValueError: not enough values to unpack (expected 12, got 10)`。

### `tools/arm_show.py` / `tools/arm_disasm.py`（50 / 58 行）

ELF32 ARM32 反汇编器（解析 phdrs → r2o → capstone `CS_MODE_ARM`）。
**32 位 ARM 下 file_offset == RVA。**

### `scripts/v557save.py`（158 行）

旧版存档读写。

CLI：`python scripts/v557save.py {info|verify|dump|hex} <path> [out]`

### `scripts/push_save_v557.py`（96 行）

### 踩坑清单

- **PowerShell 内联 `python -c "..."` 里的 `$` 和 `\` 会被吃掉**：

- PowerShell 终端是 GBK，Python 打印 emoji 报 `UnicodeEncodeError`；
  解决：`sys.stdout.reconfigure(encoding='utf-8', errors='replace')`。

   应该先做一次极大幅度改动（如钻石 9999999），看是否触发清档，
   再决定实际上限。
4. **补齐 `header` 未知字段的语义** —— 如果能解出 `header[4..10]`，也许能突破 delta 102 的上限。

## 十二、一句话总结

**旧版 v5.5.7 的存档是「14 字节头 + 大写 hex 包裹的 DES-CBC 密文 + `{`」，
DES 的 key 和 IV 都是 `PJSQJ678`；头部第 2、11 字节记录长度（单字节，上限 +102），
改档必须同步改头并用可压缩字段抵消长度变化。**
