# ES3 密钥攻关进度

## 突破：算法已 100% 静态还原（PBKDF2-HMAC-SHA1, 100 轮）

用 capstone 直接反汇编 `libil2cpp.so` 的 `AESEncryptionAlgorithm.Encrypt(Stream,Stream,string,int)`
（RVA `0x1782D44` → file `0x177ED44`），逐指令还原出完整加密流程：

```asm
0x1782dec  bl  #0x27ae80c          ; Aes.Create()
0x1782df0..0x1782e3c               ; aes.Mode=CBC / Padding=PKCS7 等属性设置
0x1782e4c  adrp/ldr r8 = [0x35e5000+0xae0]  ; ES3Internal 的某个类型句柄
0x1782e5c  bl  #0x1653d94          ; newobj Rfc2898DeriveBytes
0x1782e64  mov w3, #0x64           ; iterations = 100   <<< 关键
0x1782e68  mov x1, x20             ; password (string)
0x1782e6c  mov x2, x25             ; salt     (byte[])
0x1782e74  bl  #0x27a87e0          ; Rfc2898DeriveBytes..ctor(string, byte[], int)
0x1782e7c  ldr x8,[x24]; ldp x9,x2,[x8,#0x188]
0x1782e84  mov w1, #0x10           ; GetBytes(16) -> 16 字节密钥
0x1782e8c  blr x9
0x1782e98  ldp x9,x2,[x8,#0x1f8]; blr x9   ; aes.set_Key(key)
0x1782ea8  ldp x9,x1,[x8,#0x1c8]; blr x9   ; aes.get_IV()
0x1782ec8  mov w3, #0x10           ; 16 字节
0x1782ed4  blr x9                  ; RandomNumberGenerator.GetBytes(...) -> salt
0x1782f14  bl  #0x27a9300          ; new CryptoStream(output, encryptor, Write)
0x1782f24  bl  #0x1782604          ; AESEncryptionAlgorithm.CopyStream(input, crypto, bufferSize)
```

关键 `bl` 目标与 `dump.cs` 对照（**全部命中**）：

| 地址 | 符号 | 出处 |
|---|---|---|
| `0x27ae80c` | `public static Aes Create()` | `dump.cs:80012` |
| `0x27a87e0` | `Rfc2898DeriveBytes..ctor(string password, byte[] salt, int iterations)` | `dump.cs` TypeDefIndex 697 |
| `0x27a9300` | `CryptoStream..ctor(Stream, ICryptoTransform, CryptoStreamMode)` | `dump.cs:79739` |
| `0x1782604` | `AESEncryptionAlgorithm.CopyStream(Stream, Stream, int)` | `dump.cs:577413` |

**结论**：
```
key  = PBKDF2-HMAC-SHA1(password: string(UTF8), salt: 16B, iterations=100, dkLen=16)
文件 = salt(16) + iv(16) + AES-128-CBC-PKCS7(cipher)
```
`AESEncryptionAlgorithm` 常量（`dump.cs`）：`ivSize=16`、`keySize=16`、`pwIterations=100`。
`Rfc2898DeriveBytes(string, byte[], int)` 是 .NET 的**旧重载**，默认 HMAC-SHA1。

**仍未解出**：`password` 字符串值。salt/iv 在运行时随机生成并写入文件，所以布局可确定，
但口令本身不在 metadata 字面量、TextAsset、Unity 资源中。

### 卡住的
`support\analyzeHeadless.bat` → `support\launch.bat` → `LaunchSupport` 的 `-save` 分支
必须写 `%APPDATA%\ghidra\ghidra_12.2_PUBLIC\java_home.save`，但：

```
java.io.FileNotFoundException: ...\java_home.save (拒绝访问)
  at ghidra.launch.AppConfig.saveJavaHome(AppConfig.java:148)
```

- `-Duser.home` 被 `launch.bat:130` 强制固定为 `%USERPROFILE%`
- 目录存在时写文件失败、目录不存在时创建目录失败 → 双向死锁
- PowerShell 能写同一个路径，Java 不能 → 非 ACL 问题，是 JDK 25 在该路径的行为差异

**绕法**：完全不用 `launch.bat`，改用 pyghidra（它自带 launcher，不走 `LaunchSupport -save`）。
`LaunchSupport -vmargs` 仍可使用（不写盘），需要时用它取 VM 参数。

```
launch.bat <mode:fg|bg|debug> <jdk|jre> <APPNAME> <MAXMEM> <VMARG_LIST> <CLASSNAME> <args...>
```
